今天这期，先给一个最抓人的数字：3505 个 AI Agent，在以太坊上用真金白银连续跑了 21 天。不是模拟，不是回测，是真的链上结算。

而这篇论文给出的核心判断，恰好也是今天整个日报最重要的一句话——Agent 的可靠性，不在模型里，在模型外面那一层。

换句话说，今天大家争论的焦点，正在从"该选哪个基座模型"，悄悄转到"围着模型搭的那套执行系统，工程做得够不够深"。这一层今天有个统一的名字，叫 operating layer，操作层。

今天三篇重点论文，一篇讲真实资金下的操作层，一篇讲 Agent 安全防火墙，一篇讲代码 Agent 的 harness 重构。方向不同，但矛头一致：都在给 Agent 的执行过程加结构。

在展开之前，先花二十秒说清楚一个今天反复出现的词，叫 trajectory，轨迹。

你可以把它理解成 Agent 干一件事的完整录像：接到指令、想了什么、调了哪些工具、看到什么反馈、最后得到什么结果。过去大家只关心"最后答案对不对"，今天这三篇论文一致地把关注点挪到了这段轨迹本身——每一步是不是合理、顺序有没有异常、错在哪一环。

好，回到第一篇重点，链上 Agent 那篇。

它的实验场景是 Base 链上的 DX Terminal Pro，3505 个用户用真 ETH 出资，让 Agent 帮他们交易，跑了 21 天。这种规模的真钱真结算实验，以前基本没有。

作者最核心的发现是这样的：同样的模型，同样一段 prompt，只要你把其中一句话挪个位置，Agent 的行为就会翻车。

举个很具体的例子。他们有个版本，prompt 里第八段写了一句"每笔交易手续费 2.3%"。那个版本下，只有 3% 的推理会提到费用，Agent 正常交易。后来工程师把这句话挪到了第一段后面，结果 74% 的推理全在围着费用打转，Agent 直接不敢动了，资金趴在账上不交易。

这就是他们说的"费用瘫痪"，fee paralysis。

修法也很朴素：把这句话放进一段"代币日内本来就会波动 10% 到 50%"的语境里。只是换了个措辞和上下文，Agent 的资金部署率就从 42.9% 跳到了 78%。

这类失败他们一共总结了五种，全都不是模型不够聪明，而是 prompt 里一句软提示被当成硬规则读了，或者历史被当成了先例。

所以作者的结论是：可靠性不是模型属性，是操作层的属性。

那操作层到底是什么？就是从用户点一下滑块，到链上最终成交，中间所有环节——prompt 怎么拼、memory 怎么注入、风控怎么校验、每一步留下什么日志——全算进去。

这里还有个特别有意思的观察。他们给用户两种方式下指令：一种是自由聊天，一种是拉滑块、写明确的退出条件。结果呢，只用滑块、从不聊天的那 87 个用户，盈利比例高达 41%，是所有人里最高的。

为什么？因为滑块逼着用户把意图变成系统能检查的东西。你跟 Agent 说"帮我多赚点"，它根本不知道要对标什么。你拉一个"交易活跃度等于 5"再加一句"涨 20% 卖一半"，这就是系统可以执行、可以校验、可以追溯的指令。

对做 Agent 产品的团队，这是个非常直接的启发：能用结构化控件就别用聊天框。

另外还有个工程细节值得记一下。他们把同一套操作层搬到 Claude 4.6 上，成功率从 96% 直接干到 99.9%。说明这层功夫一旦做扎实，是可以跨模型复用的。

这也点出一个事实：如果你今天还在纠结换哪个基座，可能方向就错了——真正的杠杆在操作层。

接下来第二篇，Agent 安全方向，标题叫"行为防火墙"。

这篇要解决的问题很具体。现在 Agent 通过 MCP 这类协议调外部工具，市面上的安全网关，比如 Aegis，基本都是逐次检查：这一次调用合不合法，参数有没有问题。

问题是，攻击者早就不玩单点了。他们构造的攻击，每一步单看都完全合法，但连起来就是一次数据泄露。这种叫"上下文序列攻击"。

作者实测，这类攻击对现有防火墙的绕过率最高能到 75%。基本等于没拦住。

根源在哪？在于那些防火墙是无状态的，它只看当下这一步，不看前面发生了什么。

这篇论文的做法是：先把 Agent 正常工作的轨迹收集起来，编译成一张图。图上每个节点是"当前工具加上前几步的上下文"，边是"下一步允许干什么"。任何一次新调用，都要在这张图里找得到对应的路径，找不到就直接拦。

听起来抽象，举个例子就懂了。

一个客服 Agent 正常的工作流是：读工单、写摘要、发邮件。编译出来的图里，从"读工单"出发，唯一合法的下一步是"写摘要"。如果 Agent 被提示注入劫持了，想直接从"读工单"跳到"发邮件到攻击者邮箱"，这条边在图里压根不存在，当场拦下。

效果很猛：多步攻击和上下文序列攻击的成功率被压到 0%。

工程上还有两个亮点。

一个是延迟。所有耗时的语义分析全挪到离线做，运行时只剩查表和一次小向量比对，单次调用只有 2.2 毫秒。可以当成透明中间件塞进 OpenAI、Anthropic 的工具调用链里，几乎不影响体验。

另一个是更新机制。Agent 的工作流会演化，新工具、新流程会不断冒出来。作者的办法是默认拒绝加人工审核：遇到没见过的合法路径，人工确认后，晚上离线把这条轨迹加进图里，第二天就放行。既防漂移也防投毒。

这篇的大启发是：Agent 的安全网关，应该做成"有状态的行为画像加极低延迟执行"，而不是每一步都叫一个大模型来审查。

前两篇是可靠性和安全，第三篇讲代码 Agent 的工程架构，叫 SWE-Edit。

它盯的问题，做过 Cursor、Copilot 这类产品的团队肯定熟：让主 Agent 一边看代码、一边想方案、一边写 diff，越探索上下文越脏，而且 find-replace 格式特别脆弱，一个空格对不上就失败。

作者的做法很直接：把"看代码"和"改代码"从主 Agent 身上剥掉，各自交给一个子 Agent。

主 Agent 是项目经理，只做规划。Viewer 是读代码助理，你问它"fetch-data 里超时怎么设置的"，它从三百行文件里只挑出相关的十几行回给你。Editor 是具体落笔的工程师，你跟它说"把超时从 5 改成 10"，它自己决定用 find-replace 还是整文件重写。

两个子 Agent 各自在干净的小上下文里干活，主 Agent 永远看不到完整原文件。

结果很漂亮。SWE-bench Verified 上解决率涨了 2.1%，成本降了 17.9%。而且在 Kimi、MiniMax、GLM 这些不同的推理模型上都稳定生效，编辑成功率普遍涨了 12 到 18 个百分点。

这里有个特别值得琢磨的对比。他们做过一个实验：把 Editor 从 GPT-5-mini 换成 GPT-5，成本涨了 5.8 倍，解决率只多了 1.6%。但如果用一个 80 亿参数的小模型，专门训练它在简单改动时用 find-replace、大改动时整文件重写，效果反而能追平大模型。

结论很清楚：在 harness 层做工程，比堆模型参数划算得多。

这三篇看似在讲三件不同的事，但收回来其实是同一个故事。

链上那篇说，可靠性不在模型里，在操作层。安全那篇说，防御不能只看单步，得看整条轨迹。代码 Agent 那篇说，别让主模型什么都干，把 harness 拆开、分工做。

它们都在做一件事：给 Agent 的执行路径加结构。

所以今天最值得带走的判断是这样的——Agent 这场竞争，正在从"模型选型"，转向"操作层的工程深度"。

如果你正在做 Agent 产品，下一步真正值得投入的，不是再换一个更强的基座模型，而是把执行轨迹、工具接口、记忆层这些东西，认认真真当成工程去做。

prompt 里一句话的位置能决定 Agent 能不能赚钱，子 Agent 的拆分能让成本降两成，行为防火墙能把攻击压到零——这些都是操作层的胜利，跟模型多大没关系。

以上就是今天的 AI Agent 日报，我们明天见。
