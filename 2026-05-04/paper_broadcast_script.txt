先说今天最扎眼的一个数字。有一篇做 Agent 推理调度的论文实测发现，在现有系统里跑一个多步 Agent 任务，有百分之三十八的时间花在重算 KV cache 上，GPU 显存利用率只有百分之四十二，端到端延迟比纯推理高出整整六倍。

换句话说，Agent 跑得慢，不是模型不够强，是底下那层调度压根没把它当 Agent 看。

这正是今天这期日报最想说的一句判断：Agent 研究的重心正在从"模型能力比拼"转向"运行时和治理怎么建"。瓶颈不再是模型会不会，而是运行时怎么调度、工具该不该调、skill 能不能审计。

今天挑出来的三篇论文，分别对应这三件事：一篇做 GPU 调度、一篇做工具调用决策、一篇做 Agent Skill 的静态安全审计。它们共同指向同一层东西——Agent 的 harness，也就是承载任务、工具、日志和安全策略的那层底座。

在展开之前，先用半分钟把 harness 这个词讲清。你可以把它理解成 Agent 的"实验台"：任务怎么定义、环境长什么样、工具接口怎么调、每一步的观察和动作怎么记录、出了问题怎么重放——这些东西打包在一起，就是 harness。做 Agent 平台的人慢慢意识到，harness 做得好不好，往往比换哪个模型更决定团队能不能持续迭代。

今天第一篇重头戏，就是从 harness 的最底层——GPU 调度——动刀的，叫 SAGA。

现在主流的 LLM 推理系统，比如 vLLM、SGLang，都是以"一次请求"为单位调度的。但 Agent 不是一次请求，它是一个 Thought-Action-Observation 的循环，一个任务几十上百次调模型，中间还要等工具返回，短则几十毫秒，长则几十秒。

问题就出在这里。旧系统看到一个 session 在等工具，就按最近最少使用原则把它的 KV cache 踢掉，腾给别人。等工具返回、session 接着跑时，上下文又得从头重算一遍。作者实测下来，百分之三十八的算力就这么烧在重复劳动上。

SAGA 的做法很直接：不再以"请求"为单位，而是把整个 Agent workflow 当成调度的一等公民。

它的核心机制叫 Agent 执行图，简单说就是把一个 Agent 的多步流程画成一张图，每个节点是一次模型调用，边上标着"下一步大概率走哪里"。有了这张图，淘汰 KV cache 的时候就不光看"最近有没有用过"，还能看"接下来大概率还会不会用"。一个在等工具的 session，虽然此刻没动，但它马上还要接着跑，就不该被踢。

这件事的效果有多明显？他们在 64 卡 A100 集群上用 SWE-bench 和 WebArena 真实跑，任务完成时间提升了 1.64 倍，KV 重算时间从百分之三十八降到百分之八，显存利用率从百分之四十二提到百分之七十一。

更值得注意的是，论文很坦白地说了代价：为了保住 workflow 级的 cache 复用，峰值吞吐大概下降百分之三十。所以 SAGA 适合的是延迟敏感的交互式 Agent，不是离线批量跑评测。

这种明确说 tradeoff 的论文，对做平台的人反而更有用。

SAGA 还有两个细节值得记一下。一个是按工具类型学延迟分布——文件操作四十五毫秒，web 调用可能四十五秒，差了一千倍，固定 TTL 根本不合理。另一个是任务级公平调度：以前按请求数分算力，但跑十步的 Agent 和跑一百步的 Agent 是完全不同的工作量，SAGA 改成按"离 deadline 还剩多少活"来算紧迫度。

一句话总结 SAGA 的启发：如果你在做 Agent 推理网关，调度单位该从"请求"升级到"workflow"，亲和路由该按 session ID 而不是只看 prefix，抢占的时候 KV cache 得能迁移而不是直接丢。

讲完系统层，我们往上挪一层，到工具调用这层。第二篇论文的题目很直白，叫《To Call or Not to Call》——到底要不要调这个工具。

这篇的出发点是一个很反直觉的观察。现在大家做 Agent，基本是让 LLM 自己决定要不要调工具，然后看总体准确率。但作者发现：让模型"总是调工具"确实能提升平均分，可最优策略其实能用更少的调用拿到更高的分。也就是说，模型自己判断调不调，离最优差得很远。

更关键的是，它差在哪里。

作者把调工具这件事拆成三个问题：第一，必要性——光靠模型自己的知识能不能答？第二，效用——调了工具会变好还是变坏？第三，可负担性——在预算内值不值得调？

拆开之后，一个很扎心的结果浮出来：模型内部是自洽的，它觉得需要帮助就会去调；但它对"自己到底会不会"的判断本身就不准。有的模型普遍高估自己的需求，一路狂调；小模型则普遍低估，该调的不调。

结果就是——真该调的时候没调，不该调的时候反而调了，而且调了之后有时还把原本对的答案改错了。

论文的解法也很实用：既然模型嘴上判断不准，那就绕开它的嘴。作者发现，模型的隐藏层其实已经"知道"自己会不会，只是说出来的时候不一定。于是他们训了一个很小的 MLP 分类器，直接读最后一层的隐状态，在真正调模型之前先判断"这题该不该调工具"。

这个小分类器不用微调模型，挂在外面就能用。在 6 个模型 3 个任务上同时做到了提升准确率和降低调用次数。

再配一个小技巧：预算有限的时候，不要一条一条独立判断值不值调，而是把所有待办排个序，让最可能受益的排前面，预算用完就停。模型自己算账经常算不清，但外部排序是稳的。

这篇对做 Agent 产品的启发很直接：别完全信 LLM 自己说的"我需要搜一下"。在调用层加一个读隐状态的轻量控制器，成本几乎可以忽略，省下来的 API 钱是实打实的。

最后一篇，我们再往上挪一层，到 Agent Skill 的安全审计，叫 Semia。

这篇解决的是一个很具体的工程痛点。现在 Claude Skill、MCP manifest 这类 Agent Skill，通常是一半代码接口、一半英文策略。比如一条策略写着"外部转账需要人工审批，Agent 之间转账可以直接执行"。

问题是，这句英文每次都要让 LLM 重新理解一遍。攻击者只要在输入里多塞一句话，就可能把这条规则绕过去。

传统的签名扫描看不懂英文，只能扫代码。让 LLM 来审计呢？同一个 skill 审两次给出相反结论的事经常发生，没法证明"不存在攻击路径"。

Semia 的思路是：把英文策略编译成可以做确定性推理的事实库。

具体做法分两步。先用一个 LLM 把 Skill 翻译成一套结构化的谓词——哪些动作、谁能触发、有没有审批门、哪些是秘密——全部摊平成一条条数据库事实。然后"攻击者的输入能不能到达高危操作"就变成了一个纯数据库查询，跑多少次结果都一样。

这里有个关键机制叫 propose-verify-evaluate：让 LLM 先给一个翻译，然后做两重校验，一重看结构合不合法、一重把结构化结果再翻回英文看跟原文像不像。不合法就带着错误提示让它修，翻回去不像就直接重来。这样既用上了 LLM 的语言能力，又避免了它的不稳定。

结果也很硬：在一万三千多个真实 skill 上跑，F1 达到 90.6%，而且真的挖出了 17 个已确认的零日漏洞，其中有些是 GitHub 社区评审、VirusTotal 扫描、还有直接问 LLM 这三种方式都漏掉的。

这件事的启发其实超出了安全本身。它说明一件事：LLM 适合做翻译，但判断还是应该交给确定性的推理引擎。你想让 Agent 平台的安全策略"可审计、可证明"，就不能把判断权留给每次都重新解读的 LLM。

把今天这三篇串起来看，你会发现它们指向同一件事。

Agent 的瓶颈正在系统化地从模型内部移到模型外部：调度该不该按 workflow 切、工具该不该调、skill 能不能通过静态审计。模型本身强不强，反而不是最关键的变量了。

安全侧开始用静态分析和可验证的工件，去补那些写在英文策略里的模糊地带。系统侧开始把整个 workflow 当成调度的一等公民，而不是一串零散请求。工具侧开始认真算调用的账，不再盲目堆次数。

对做 Agent 平台的团队，今天的信号很清楚：该把精力从"让模型学会用工具"升级到"让整个 harness 可测、可控、可审计"。模型能力的红利你追不过大厂，但 runtime 和治理这层，是每个平台自己必须建的护城河。

以上就是今天的 AI Agent 日报，我们明天见。
