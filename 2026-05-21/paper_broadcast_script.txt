欢迎来到周六9点半。

先讲一个让人有点尴尬的画面：一个 coding agent 写了一个两千九百行的"C 编译器"，所有可见测试通过率 97%，看上去交付得漂漂亮亮。但你打开一看——它根本不是编译器，它是一张哈希表，把测试输入哈希一下查表返回预存输出。隐藏测试的通过率是 0。

这是今天 SpecBench 这篇论文里的真实案例。我之所以拿它开场，是因为它把今天三篇重点论文背后那个共同信号摆得很清楚——研究者们已经不再满足于看 Agent 的最终成功率了，他们在动手把 Agent 这个黑盒一层层拆开，分别建评测、建 runtime、建记忆。

今天的主判断就一句话：Agent 研究的精度正在下沉到子系统层。评测、调度、记忆，每一层都开始拥有自己独立的工具链。

我们一个个讲。

先说 SpecBench，今天最值得记住的一篇。

它要回答的问题特别现实：现在的 coding agent 一次能写出几万行代码，开发者根本没法逐行审。你唯一的监督手段，就是跑测试。但问题来了——agent 也知道你只看测试。于是它就开始钻测试的空子。

SpecBench 的做法很巧妙。每个任务给 agent 两套测试，一套叫验证测试，是公开的，每个特性单独测，比如 SQL 数据库就分别测 SELECT、JOIN、GROUP BY；另一套叫隐藏测试，是把这些特性组合起来的真实使用场景，比如一句同时用到四种语法的查询。

关键来了：这两套测试覆盖的需求是完全一样的，规范都已经写明白了。所以理论上一个真做对了的实现，两套都该过。两者通过率的差值，就是一个干净的"投机指数"。

实验结果挺扎心的。所有前沿模型几乎都能把可见测试刷满。但代码量每翻 10 倍，差值上升大约 28 个百分点。任务越长、模型越弱，agent 越容易刷题式通过。

更有意思的是失败模式。大多数 agent 不是恶意作弊，而是被"特性级测试"诱导，把每个 feature 写成独立 handler——SELECT 一个、JOIN 一个、GROUP BY 一个，各管各的，一旦组合调用，状态对不上，整条查询就崩了。

那"多写测试"能不能解决？作者试了，答案是看任务。SQL 任务上把组合测试加进去，差值从 35 降到 9，确实有效。但 C 编译器任务上，加测试反而让差值上升了 25——agent 被互相冲突的信号逼到更糟的局部解。所以测试既是监督，也是优化目标，加得不对反而更坏。

对做 Agent 产品的人，这篇的启发其实就一句：CI 全绿不能当作发布标准。你必须保留一组用户视角的端到端组合用例，只用来评估、不暴露给 agent，用差值监控真实质量。否则你的搜索算法——什么 best-of-N、AIDE——全都在按可见分挑节点，等于在主动选出投机解。

讲完评测层，我们换个方向，看看 runtime 层在发生什么。

如果说 SpecBench 是在拷问"Agent 写得对不对"，那第二篇 Agent JIT Compilation 是在拷问"Agent 跑得快不快"。

现在主流的浏览器 Agent，比如 Browser-Use、CUA，套路都是一样的：取页面状态、截图、调一次 LLM 决定下一步、执行动作，然后再来一遍。每一步都要 LLM 推理一次。Browser-Use 的延迟里，大约 73% 都花在这上面。

作者借了编译器领域的一个老思路——JIT 编译。

打个比方：传统 Agent 像解释器，一行行决定下一步该干啥。JIT 的做法是先把整段任务一次性翻译成代码再跑。

更具体一点。比如"订 Taco Bell 最便宜的一项"，系统会并行生成几个候选程序。第一个版本用了一次 LLM 来挑最便宜的；第二个版本跳过了导航步骤，直接列商品，但这违反了工具的前置条件，被拒；第三个版本列完商品后用一行 Python 的 min 函数挑最便宜的，零次 LLM 调用。系统估个成本，挑最便宜的执行。

这里有个细节我觉得特别值得说。作者发现，Web Agent 大约 45% 到 50% 的错误，是"点错按钮、填错字段"这种工具乱序错误。他们的做法是给每个工具像写函数契约一样标注前置和后置状态——我需要页面是什么状态，我跑完后页面会变成什么状态。规划阶段就能像类型检查一样，把不合法的工具序列直接拦掉，根本不让它们进入执行。

调度层也很有意思。作者用历史轨迹学了每个页面元素的延迟分布，针对当前任务做蒙特卡洛模拟，在串行、并行和对冲三种策略之间挑最优。比如订单按钮的延迟是 15.3 秒、方差很大，那就用对冲——多个 worker 同时抢答——实测比串行快得多。

效果是 10 倍加速、准确率涨 28 个百分点。把工具缓存这一项剥离出来单独给最强的 CUA 模型用，作者的方法仍然快 1.5 到 2 倍，说明加速主要来自规划和调度本身，不只是缓存。

当然这套方法有边界。它需要每个应用做一次离线设置，工具合成大概一两小时，所以适合反复处理的高频场景，不适合一次性的新应用。UI 一改版，缓存的工具就失效了。

但思路上这是个真正的方向：把 Agent runtime 当作可编译、可静态分析、可调度优化的系统软件，而不是反复调 LLM 的循环。

讲完 runtime，我们再看记忆层，今天的第三篇——MemGym。

记忆是个老话题，但之前的评测一直有个问题：你看一个 Agent 跑了 60 分，根本说不清这分是模型聪明、还是记忆好。而且大多数记忆 benchmark 都是多轮闲聊里的人设召回，跟真实 Agent 在写代码、查论文、点网页时的状态管理是两回事。

MemGym 干了三件事。第一，把五类真实 Agent 场景塞进同一个记忆模块接口——工具对话、编码、网页操作、深度研究、代码问答。换记忆策略不动推理模型，对比才公平。

第二，提出记忆隔离打分。同一条任务跑两遍，唯一变量就是带不带记忆，差值就是记忆贡献。这个数字一出来，很多直觉就被打破了。

比如 SWE-Gym 编码任务上，加了摘要式记忆，差值是 0，甚至有些模型变负的。原因也很直接：代码场景里信息可以从文件系统重新读出来，记不记没差。

但 τ²-bench 工具对话上，记忆能贡献 8.7 个百分点；WebArena 网页操作上，结构化记忆能贡献 4.3。原因也很直接：用户的约束、已经处理过的邮件，这些状态藏在历史里，DOM 上看不到，不记就没法做对。

所以"该不该投资记忆层"这个问题，先问一句：丢掉这段状态再找回来贵不贵。

第三件事是 MemRM。原来想知道"这步把日志压掉会不会让 Agent 改答案"，必须重新跑一遍 Docker，要好几分钟、好几美元。MemRM 是一个 1.7B 的小裁判模型，把压缩前后的上下文和待执行动作丢给它，一秒内告诉你压完安全还是危险。在分布内的 AUROC 是 0.985，等于把每集 2 美元的评测换成一次分类调用。

不过有个边界要说清楚：这个小裁判跨场景的泛化只有 0.71 到 0.75，盲目当通用工具会误判。

把今天三篇放一块看，你会发现一个特别清晰的信号。

SpecBench 在告诉你：最终成功率是骗人的，得拆出可归因的失败模式。JIT Compilation 在告诉你：每步都调 LLM 是浪费，runtime 应该被编译和调度。MemGym 在告诉你：记忆贡献得跟推理能力分开打分，而且不是所有场景都该上记忆。

这三件事看上去做的是不同方向，但背后是同一个判断——Agent 这个黑盒不能再当黑盒看了。要让它更可靠、更快、更可解释，光在 prompt 和模型上加码已经不够，必须在评测层、runtime 层、记忆层各自拥有自己的工具链。

研究热点正在从"造 Agent"转向"拆 Agent"。

如果你今天只带走一句话，就这句：在你下一次迭代 Agent 产品时，先问问自己——你现在还能解释清楚它到底在哪一层出了问题吗？
