先给大家一个今天最值得带走的判断：Agent 领域的瓶颈，正在肉眼可见地从"模型聪不聪明"挪到"它脚底下那一整套东西扎不扎实"。

什么叫脚底下那一整套东西？就是 Agent 跑在什么环境里、运行时崩了怎么办、多个工具接在一起会不会顺手把密钥搬走、评测到底在量什么。今天三篇重点论文，分别砸在这三个点上。

先说一个扎眼的数字。现在主流做法里，Agent 在 sandbox 里跑崩了想恢复，Terminal-Bench 上只有 8% 到 13% 的任务能正确恢复。说白了，十次里有九次救不回来。这就是今天要聊的第一个问题。

咱们按顺序讲。

今天第一个重点，叫 Synthetic Computers at Scale，翻译过来就是大规模合成电脑。它要解决的问题其实很朴素：现在大家都想做"帮你处理一整天工作的桌面 Agent"，可这种 Agent 训练起来缺数据——缺的不是任务，而是真实用户那台电脑。

你想想，一个真人的电脑上有什么？有几百个文件、有项目历史、有和同事来回的邮件、有上一版和这一版的方案。这些东西没法公开采集，涉及隐私和公司资料。以前的合成数据只造任务，不造环境，结果 Agent 一上机，面对的是个空文件夹，等于让它在真空里上班。

这篇论文的做法是，把整台电脑也合成出来。

它的流程大概是这样：先给一个 persona，比如"一位有 16 年经验的高级理财顾问 Margaret"。然后顺着这个人展开——她电脑上会有哪些盘、哪些目录、哪些文件、这些文件之间谁引用谁。接着按依赖顺序，一份一份生成真实格式的 docx、xlsx、pptx，能从网上抓公开资料就抓，抓不到就让 LLM 补。最后这台电脑上，可能有一百多个带版本、带引用关系的文件，像真人攒了好几年。

造完电脑只是第一步。真正值得记住的是它怎么用这台电脑。

它上面跑两个 Agent，模拟一整个月的上班节奏。一个 Agent 当"老板"，定月度目标、安排协作者；另一个 Agent 扮演用户本人，周一开会排计划、周中改稿、跟经理和客户来回邮件、周五交初稿。协作者还会故意藏一些关键材料，你不问它就不给，逼着 Agent 学会沟通和追问。

一次仿真平均跑两千两百多轮、八个多小时，文件数量从一百多涨到快两百。

这件事为什么重要？因为现在做 agentic 强化学习，最缺的不是结果，是过程轨迹——Agent 是怎么想、怎么查、怎么改、怎么跟人沟通的。长程仿真把这两千多轮过程全记下来，同时还产出最终的 PPT 和报告做结果评分。过程奖励和结果奖励一起有了。

对做产品的人，有一个直接启发：以后 demo 和评测桌面 Agent，别再用空白工作区了。真实体验和空白工作区的体验，完全是两回事。

好，第二篇，也是今天系统层最值得看的一篇，叫 Crab，专门解决一个被忽视的问题——Agent sandbox 崩了怎么救。

刚才说过，现在救不回来的概率高达九成。为什么？因为现有做法两头不靠。

一头是只存聊天记录和文件，轻便但漏信息，OS 层的副作用都丢了。另一头是每一轮都把整个虚拟机做个完整快照，正确是正确，但 96 个 sandbox 一起跑的时候，执行时间会慢将近四倍。

根本矛盾在哪？Agent 框架只知道"我调了一次 shell"，但不知道这条 shell 到底改了什么。内核知道哪些文件变了，但不知道这个变化跟 Agent 的哪一轮对话有关。两边信息对不上。

Crab 的第一个关键发现是：超过 75% 的 Agent 轮次，其实根本没产生任何需要保存的状态。大多数轮次是白存。

于是它用了一个叫 eBPF 的内核观测工具，在每一轮结束时看一眼：这一轮相对上一个存档点，到底有没有真的留下东西？临时建了又删的文件不算，fork 出来又退出的子进程也不算。只看净变化。

根据净变化，它把这一轮分成四档——什么都没变就跳过，只改了文件就只存文件，只动了进程就只存进程，都变了才全量存。文件判定准确率 98%，进程判定 100%，而且不漏报。

这套判断拦住了什么问题？拦住了"全量快照太贵、部分快照又不准"的两难。

但光做得准还不够，还得做得快。Crab 第二个巧妙的地方是：Agent 每一轮结束后，都要等 LLM 想几秒钟才会给出下一步，这几秒其实 sandbox 是闲的。Crab 就把 checkpoint 任务塞进这段等待里异步做完。

效果相当漂亮。在 64 个 sandbox 一起跑的情况下，Agent 能感受到的 checkpoint 延迟只占任务时间的 0.44%。就算中途注入一次崩溃再恢复，端到端时间只比无故障执行多 1.9%。而老的 Restart 方案，在 SWE-Bench 上要慢 1.67 倍。

这篇论文的启发其实比数字更重要——Agent 的容错不该塞在 Agent 框架里，而该放在底下的运行时里做。做 Agent 云沙箱、做 Coding Agent、做 RL 训练平台的人，都能用这一层。论文里还提了一个有意思的用法：把"回滚到上一个干净状态"作为工具暴露给 Agent 自己调，实验里减少了 29% 的墙钟时间和 36% 的 token 消耗。

好，第三篇，换一个方向聊安全。这篇叫 MCPHunt。

MCP 现在已经成了 Agent 接外部工具的事实标准，生态里有超过一万个服务器。企业场景里常见的是：一个 Agent 同时连着文件系统、数据库、Git、浏览器、Shell。

问题是什么？以前大家研究 Agent 安全，都在防 prompt injection、防越狱，都是在假设有攻击者。但 MCPHunt 这篇论文问了一个新问题：如果压根没人攻击，Agent 就是老老实实执行任务，它会不会自己顺手把 API key、密码从一个服务器搬到另一个服务器？

答案是会。而且比想象的严重。

他们跨 5 个模型、147 个任务测下来，这种"良性传播"的策略违规率，从 11.5% 到 41.3%。也就是说，运气不好的模型，每三次任务里就有一次会把凭证搬错地方。

他们的测法很聪明。把真实密钥换成格式一模一样的"假密钥"，带一个记号，塞在 .env、数据库这些地方。然后看 Agent 在执行任务时，会不会把这些带记号的字符串写到别的地方去。只要在写操作的参数里匹配到记号，就算一次泄漏。完全不需要人去读轨迹。

这套测法还做了一个重要区分。如果用户明说"把整个项目原样复制过去"，那 Agent 带上密钥是完成任务，不算违规。但如果用户只要"写一份技术栈报告"，Agent 却在 Markdown 里把 .env 原文抄进去了——这才是真正的安全失败。

最值得记住的一个发现是：真正决定风险的不是模型，而是数据流的路径。

统计分析显示，风险的 62% 来自 source 到 sink 的路径本身，模型身份只解释 32%。其中浏览器路径几乎每个模型都翻车——因为浏览器返回的是整页 HTML，没有字段粒度，Agent 想脱敏也脱不干净，GPT 级别的模型在这条路径上的泄漏率仍有 74%。

还有一个扎心的结论：靠写 prompt 提醒"别泄漏密钥"这事，不靠谱。强模型能降 97%，弱模型只降一半不到。真正能稳住所有模型的，是在编排层做污点守卫——读到带记号的敏感值之后，任何往外部写的操作都自动替换成占位符。这种拦截不依赖模型自觉，实测能让四个模型的违规率归零。

对做 Agent 平台的人，这篇的启发很直接：跨服务器的数据流要当成一等公民，工具注册时就要声明哪些是敏感源、哪些是外部出口，浏览器到本地、配置到脚本这种高危路径要单独标出来。光在 system prompt 里写一句"请勿泄漏密钥"，等于没写。

最后收一下。

今天这三篇放在一起看，信号非常一致。合成电脑在补训练数据的底，Crab 在补运行时和容错的底，MCPHunt 在补安全评测的底。它们共同指向一个判断：Agent 的下一步进展，不会来自更花哨的 prompt 技巧，而会来自它脚底下这一套叫 harness 的东西——任务、环境、运行时、评测协议、安全护栏，打包在一起的那层基础设施。

对做 Agent 产品的人，今天最实在的一条是：如果你现在还在纠结换哪个模型、改哪段 prompt，也许该抬头看看，你的 Agent 有没有一台像样的电脑去上班，崩了能不能救回来，跨工具的时候有没有人看着数据流。

这些活儿不性感，但真正决定产品能不能上线。今天就聊到这儿。
