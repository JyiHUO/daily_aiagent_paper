先说今天最值得记住的一个数字：Claude Code 这种编码 Agent，真正决定效果的代码里，只有百分之一点六是 AI 的决策逻辑，剩下百分之九十八点四，全是包在外面的那一层工程代码。

换句话说，今天我们用的 Agent 好不好用，九成九不取决于模型多聪明，而取决于外面那层怎么搭。这也是今天三篇重点论文共同指向的判断。

今天的主线非常清晰：Agent 研究的重心，正在从"模型能力"彻底转向"执行链和系统边界"。大家不再卷底座有多大，而是在卷外面那层怎么调、怎么守、怎么在真实屏幕上不翻车。三篇论文分别对应三件事：运行时调优、跨会话安全、还有桌面 Agent 的执行稳健性。

先讲第一篇，也是我今天最想让你记住的一篇，叫 HARBOR。

它讲的是一个很现实的困境。长程 Agent 外面那层工程代码，包含几十个开关——要不要压缩上下文、缓存怎么做、要不要记忆、要不要提前预测下一个工具调用。工程师原来的做法，是加一个开关、跑一次评测、看通过率，再决定留不留。

问题是这种手工调优，一旦开关超过几个，就基本必翻车。

作者在摩根大通一个真实生产 Agent 上做了四轮规范的手工调优，只有一轮真的比基线好。更扎心的是他们查日志发现，有些功能其实根本没跑起来——有个跨容器的记忆模块，命中计数从头到尾都是零；还有个工具预测器，压根就没被调用过。但手工看通过率表，完全看不出这些静默 bug。

还有更离谱的：一个上下文压缩模块被接错了位置，接在了缓存的上游，结果缓存里存的全是压缩摘要，后续任务去 grep 行号的时候，根本看不到原始内容，于是全错。

作者的判断是：这事不能再靠人调了，得交给贝叶斯优化器去搜。

他们的做法是把这几十个开关当成一个高维配置空间，然后用一个带约束的优化器去搜最优组合。里面有两个细节特别实用。

一个是成本分层。先在八个任务的小集合上便宜试错，看起来有戏的配置才拿去跑完整集合，不浪费预算。另一个是安全闸——优化器推荐的任何新配置，上线前必须在统计意义上不比原来的基线差，否则直接拒掉。这刚好挡住了那种"论文里 work、搬到你这就变负收益"的坑。

对做 Agent 产品的人，启发很直接。第一，每个功能模块都要有独立的请求和命中计数，不然静默失效你永远发现不了。第二，压缩和缓存的先后顺序必须想清楚，不能让摘要污染了上游状态。第三，换模型、换场景，都应该重新跑一遍自动搜索，而不是凭感觉拍一套配置带走。

不过这篇论文自己也承认，结论是"小样本小范围"的——只在一个 benchmark、一个模型、一个 Agent 上验证过，而且最好那轮也只比基线多通过两个任务，已经很接近噪声。所以它更像是一个方法论上的宣言：harness 调优该被当成机器学习问题，而不是工程直觉问题。

好，第二篇，叫《跨会话威胁》，讲的是 Agent 安全里一个结构性的盲点。

先记一个判断：现在所有 Agent 的守门员，都是没有记忆的。

什么意思？每条消息进来，守门员单独判断一次——这条有没有越界？但攻击者早就学聪明了。他不会一次性让 Agent 干坏事，而是把整个攻击拆到几十上百个会话里。第一次让 Agent 列一下文件，第二次让它读个配置，第三次做个摘要，第四次发到外部一个 URL。每一步单看都是 DevOps 日常工作，合起来才是完整的数据外泄。

Anthropic 在 2025 年披露的那起事件已经证明，攻击者光靠"拆解"，就能绕过所有单回合的安全检测。

那直觉上，是不是把所有会话都拼在一起，塞给一个长上下文模型一把梭，就解决了？

作者用实验打脸了这个想法。他们试了这种"拼全部日志"的方式，结果在真正的跨会话场景下，召回率直接腰斩。不是塞不下，是模型在长对话里注意力会稀释，攻击片段被大量正常工作一包围，就漏检了。更糟的是，这种拼接本身还会被攻击——攻击者可以故意设计文本，让拼起来之后正好变成对审计模型自己的 prompt 注入。

他们的方案叫"核心集记忆读取器"。

简单说就是：不要贪多，只保留五十条最有信号的历史片段，按固定顺序拼在提示词末尾，然后让模型基于这个浓缩版做跨会话关联。这里有个很聪明的工程细节——因为顺序固定，前面的缓存可以直接复用，不用每次都重算，实时成本可以降一个数量级。

对做 Agent 安全的人来说，这篇的启发有两条。一是守门员不能再做成纯单消息分类器，必须在 Agent 的长期记忆、RAG 索引、多 Agent 共享的黑板上，都加跨会话关联。二是检测要放在 Agent 真的要执行那一刻，而不是等日志落库之后再去 SIEM 里事后关联——等你关联完，数据早就发出去了。

当然这篇也有明显限制，整个 benchmark 每个子集只有五十四个场景，绝对数字不能直接外推到生产。但它第一次把"跨会话检测"当成一等问题来建模，这个方向值得持续追。

第三篇叫 VLAA-GUI，是做桌面 Agent 的。

这一篇的卖点很直接：在 OSWorld 这个桌面操作基准上，它首次单次通过率做到了 77.5%，超过人类的 72.4%。而且用的还是十五步预算，打平了别人五十步的系统。

它到底解决了什么？两个所有桌面 Agent 都有的老毛病。

第一个叫"假完成"。Agent 改完一个设置就宣布完工，其实文件没保存、开关没切、另一个母版还没改。论文里一个扎心的数据是：失败任务里超过 86% 都是这种"我以为我做完了"。

第二个叫"死循环"。同一个按钮点十几次，也不换思路。

他们的做法很朴素，就是把"判断是否完成"这件事，从模型的主观感觉，变成一张必须逐项打勾的清单——而且要两个人签字才算数。

一个是 Agent 自己每走一步都要对着截图自检，另一个是独立的裁判模型在 Agent 想要收工时，再核一次视觉证据。证据不够，就把拒绝理由写回去让它继续做。

论文里那个 LibreOffice 改页码颜色的例子特别典型。Agent 改完一个母版就说做完了，裁判一看——颜色还是灰的、文件也没保存，拒了。Agent 按了保存再说做完，裁判又拒，因为还有另一个母版没改。这时候 Agent 调了一个外部的文本搜索工具，问"怎么在 Impress 里改页码颜色"，返回的教程里有一句关键话："如果有多个母版，每个都要改"。这条信息光看屏幕是看不出来的。

至于循环破除，他们做成三级熔断。同一个按钮连续点没反应，先换种点法，比如快捷键换菜单。整屏幕状态都在原地转，就要求换整体策略。再不行，一个外部裁判直接把那个让它上瘾的动作拉黑。

对做桌面 Agent 产品的人，这篇启发非常直接：完成判定和循环检测，应该做成独立的强制模块，而不是交给主模型自己感觉。尤其是删除、发送、支付这种关键操作，必须有外部确认。

不过这里有个反直觉的发现值得注意：工具不是免费的，每次调用都要花动作步数。强模型调工具稳赚，省下的无效步比调用成本还多；但在弱模型加紧预算的情况下，加这些工具反而会掉十个点。所以这套框架并不是对所有模型都通用，要和预算、backbone 一起调。

今天讲到这，三篇论文其实可以合起来看。

HARBOR 告诉你，Agent 外面那层工程开关已经多到人脑调不过来，得交给优化器。跨会话威胁告诉你，Agent 的安全边界不是单条消息，而是跨几十个会话的时间维度。VLAA-GUI 告诉你，Agent 的执行稳健性，关键不在让模型更聪明，而在于外面那层能不能拦住"假完成"和"死循环"。

三件事指向同一个判断：Agent 不再是一个"模型能力问题"，而是一个系统问题。它由执行链、工具层、评测层、安全层共同构成，任何一层掉链子，整条都崩。

所以接下来真正有开拓性的研究，大概率不会是再加一点 prompt 技巧，而是重新定义 Agent 应该怎么被评测、怎么被约束，以及怎么在真实环境里更稳地跑下去。

如果你今天只带走一句话：Agent 的胜负手，已经不在模型里了，在模型外面那一层。

以上就是今天的 AI Agent 日报，我们明天见。
