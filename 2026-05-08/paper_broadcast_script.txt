先说今天最值得记住的一个数字：在 SWE-bench 上，一个 Coding Agent 跑 75 步才能解一道题，现在有人在模型内部加了一个钩子，同一道题只用 55 步就解完了，解题率反而还涨了六个点。关键是，这个改动既不用重训模型，也不用改一行 prompt。

这就是今天 Agent 研究的一个很明显的转向：大家不再把 Agent 的可靠性问题当成"提示词没写好"来补救，而是直接下沉到运行时——进到模型的隐藏激活里、进到执行轨迹流里，去实时观测和纠偏。

换句话说，过去一年大家搭 Agent 靠的是越写越长的 system prompt 和一层层反思循环；而今天出现的这三篇论文，指向的是完全另一种形态的护栏：可审计的监控器，加上激活层的钩子。未来 Agent 框架的稳态控制，可能不再是 prompt 工程师的活，而是 runtime 工程师的活。

我们今天就围着这个趋势讲三篇论文。第一篇最硬核，先展开讲。

第一篇叫 TACT，做的事情是给长程 Coding Agent 治两种病：想太多和做太多。

想太多，是 Agent 明明已经读过 models.py 了，过了几十步又反复推理同一段代码在干嘛。做太多，是 Agent 没消化上一轮工具的返回，就又发一个 grep 出去。两种毛病加起来，就是我们熟悉的长程 Agent "越跑越糊"。

过去的做法，像 Reflexion、Self-Refine、Tree-of-Thoughts，都是把模型当黑盒，在外面加一层反思或者搜索。错已经犯了，才回头打补丁。

TACT 的做法不一样。作者先问了一个问题：这种漂移，在模型内部有没有痕迹？

答案是有。他们把每一步打上标签——这一步是带来了新信息，还是在重复老信息——然后去看模型在吐 token 那一刻的隐藏状态。结果发现，"想太多"和"做太多"这两种失败，在高维激活空间里各自朝一个方向飘，而且这两个方向基本能线性分开，判别的 AUC 接近 0.9。

这就意味着，漂移不是一种虚的行为描述，它在模型内部是一个可以测量的向量。

接下来就简单了。作者在模型的前十层挂了 forward hook，每当 Agent 要做决策的时候，就看一眼当前的隐藏状态在这两个方向上偏出去多远。偏得太多，就把它往回拉一点。他们给了三种拉法：一种是"限速带"，只在明显越界时拉；一种是每一步都轻轻拉一下；一种是折中。

效果是什么呢？在 SWE-bench Verified 上，基线解题率 67%、平均 75 步；加了这个钩子之后，解题率涨到 73%，步数降到 65。而限速带那一档，步数直接砍到 56 步，几乎省了四分之一的工具调用。对比之前最强的反思类方法 AgentDebug，TACT 不用多跑一轮、不用重试，零额外成本，还多拿三个点。

这件事对做 Agent 产品的人意味着什么？

意味着你可以在不动 prompt、不加重试的前提下，直接把"反复读同一个文件"这类典型浪费压下去，token 成本和 tool 调用成本一起降。更重要的是系统层面的启示：Agent 框架里可以专门留一层，叫"步级漂移检测"。用离线标注把漂移方向学出来，在线上推理网关挂钩子。相当于给 Agent 装了一个内生的自动驾驶辅助，车要偏出车道时方向盘自己会回一点。

当然，这招目前只对开源模型有效，因为闭源 API 你拿不到 hidden state。但这个方向本身，是过去一年 Agent 可靠性研究最清晰的一次下沉。

讲完模型内部，我们跳到另一个极端——评测。

第二篇叫 MANTRA，解决的是行业 Agent 落地绕不开的一个痛点：合规评测。

想象你在做一个航司客服 Agent，或者企业采购 Agent，它身后是一本几十页的 SOP 手册。Agent 每一次工具调用，都可能踩中某条规则。怎么测它守不守规矩？

现在主流是两种办法，都有明显短板。一种是人工造题，规则变一次基准就废一次，根本扩展不动。另一种是让另一个大模型当裁判，但在几十步的工具调用序列里判"你这一步有没有违反前置条件"，大模型其实很不可靠。

MANTRA 的思路很有意思：不让大模型当裁判，让求解器当裁判。

具体怎么做？同一段手册，让 LLM 用两种完全不同的方式描述。一种是 trace 层面的检查规则，比如"分配仓库拣货员必须在检查库存之后调用"。另一种是符号化的世界模型，写清楚每个工具的前置条件、每个状态之间怎么转移。

然后把这两套东西都编译成 SMT 公式，丢给 Z3 求解器去找矛盾。如果求解器能构造出一条轨迹，满足检查规则、但违反世界模型的前置条件，那就说明两边里至少有一边写错了。

这背后的直觉是：LLM 生成一次出错是常事，但让它用两种完全不同的表达方式独立生成，两边同时犯一模一样的错误，概率就很低。于是求解器抓到的矛盾轨迹，基本就是高质量的修复信号。

修的时候也有讲究。作者不是让 LLM 自由改写，而是走一个分诊流程：先看这批矛盾是不是因为世界模型少了一个共享的前置条件，如果是，就一次性补上，所有相关场景一起通过。剩下的才逐个改检查规则。所有修改都走一个受控的编辑语言，避免 LLM 自由改写时又引入新错误。

最后产出的是 285 个任务、完全确定性评分的 benchmark——Agent 每一步对不对，布尔值说了算，不用再问 GPT。

对 Agent 评测栈的启示很直接：以后做金融、医疗、航司这类合规严苛场景的 Agent，别再只靠 LLM 裁判了。SOP 手册本身就可以自动转成可机器检查的约束集，用来做回归测试和上线把关。更大一点看，这是一种 neuro-symbolic 的组合模板——LLM 负责把自然语言变成符号，求解器负责找不一致——这套东西完全可以推广到 Agent 运行时的 guardrail 检查里。

讲到运行时 guardrail，第三篇就接得很自然。PrefixGuard，做的是在线失败预警。

它要解决的痛点也很现实：Agent 跑一个长任务，往往要到最后一步 verifier 才告诉你失败了，那时候早来不及干预了。想每一步都调 LLM 裁判吧，成本又顶不住。

PrefixGuard 的做法是把这件事变成一个数据问题：我手上有历史的 trace，加上每条 trace 最后成没成的标签，能不能从里面学出一个轻量的在线打分器？

它分三层。最底层叫 StepView，用 LLM 一次性离线生成一个确定性解析器，把浏览器、终端、对话这些长相完全不同的原始 trace，统一解析成七个字段——工具名、参数、返回值、状态这种。适配器生成完就冻结，线上再也不调 LLM，成本归零。

中间一层，把这些 typed step 学成一串离散的事件符号——你可以理解成模型自己发明了一套小字母表，专门用来描述"Agent 正在发生什么"。然后一个 GRU 在这串符号上打分，输出当前轨迹走到此处有多危险。

最有意思的是第三层——作者没有只报 AUPRC，而是追问一句：这分数排得好，拿去当警报用了吗？

他们设了一个很实际的阈值：在正常轨迹里假警率不超过 10%，这时候看失败轨迹能不能被提前发现。结果很反直觉：WebArena 的 AUPRC 高到 0.9，看着很漂亮，但在 10% 假警率下，提前预警的召回只有不到百分之一——基本等于只能在快崩的最后一刻喊一声，根本来不及干预。反而是 TerminalBench，AUPRC 数字更低，却能在任务还剩 21.5% 步数的时候给出可信警报，这才是真的能触发回滚、能切 safe-mode 的监控器。

这个点对做 Agent 护栏的团队很关键：上线验收指标不能只看 AUPRC，要看低假警率下的首次预警提前量。监控器"会排名"和"能干预"，是两件完全不同的事。

好，三篇讲完，我们回到开头的那个判断。

TACT 在模型激活里实时纠偏，MANTRA 用求解器把自然语言手册变成确定性评测，PrefixGuard 把执行轨迹变成在线警报——三篇论文看起来各做各的，但合起来其实是在回答同一个问题：一个长程 Agent 在运行时，要怎么被观测、被纠偏、被约束。

过去我们给 Agent 加能力，习惯性地去加 prompt、加反思、加工具。今天这三篇告诉你，下一代 Agent 的稳态，要靠三件东西撑起来：模型内部的激活钩子、可机器检查的合规约束、trace 流上的在线监控器。

如果你正在带一个 Agent 产品团队，今天可以带走一个很具体的行动建议：回去看一眼你们现在上线前的验收清单。如果里面还只有"准确率"和"任务成功率"，那你大概率落后了半年。真正要加的，是低假警率下的提前预警召回、是 trace 级的确定性 check 覆盖率、是运行时漂移的分布统计。

护栏的形态正在变。以后一个 Agent 系统够不够靠谱，可能不看它的 system prompt 有多长，而看它的监控器有多深。
