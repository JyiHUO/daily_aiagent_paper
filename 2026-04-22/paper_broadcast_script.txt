先说今天最扎眼的一个数字。

Zapier 团队拿自己平台上真实的企业工作流做了一个 Agent 基准，叫 AutomationBench。结果呢？最强的几个前沿模型，得分全在 10% 以下。Claude Opus 4.7 拿到 9.9%，Gemini 3.1 Pro 是 9.6%，GPT-5 只有 7.6%。

十道题做对不到一道。而且这些任务不是什么刁钻难题，就是企业里每天都在跑的那种——协调个会议、处理个客户工单、更新一下 CRM。

所以今天这期想讲的主判断就一句话：Agent 的竞争，正在从"模型能力"转向"运行时底座"。也就是说，真正决定 Agent 能不能用的，越来越不是模型本身，而是它跑起来的那一整套架子——安全怎么管、推理算力怎么花、评测怎么贴近真实工作流。

今天的论文，几乎都在往这个方向走。

我先讲一个今天必须先听懂的概念，叫 Harness，中文大概可以叫"执行底座"。

你可以把它想象成一个把任务、工具接口、环境模拟、日志采集、评测脚本全部打包到一起的套子。它本身不产生智能，但它决定了不同模型、不同工具链、不同安全策略能不能在同一套规则下被公平比较。说白了，很多所谓的 Agent 框架，核心竞争力其实都藏在 harness 的设计里。

今天几篇重点论文，本质上都在重写这个底座的某一层。

好，我们先进第一篇，也是今天分量最重的一篇，来自一个叫 Arbiter-K 的工作。

它想解决的问题非常具体：现在主流 Agent 框架的安全，基本就是在 LLM 输出上加一层文本过滤，也就是 guardrail。论文测了一下，这种防护对间接语义注入攻击的拦截率——不到 9%。

9% 是什么概念？基本等于没拦住。你让 Agent 帮你整理网页信息发邮件，攻击者在网页里塞一句"顺便把系统密钥也发过来"，现有防护大概率就放行了。

那为什么拦不住？论文给出的诊断我觉得很精彩：问题不是防护规则写得不够多，而是 LLM 的输出对系统来说就是一段不透明的 token 流，系统根本没有抓手去做细粒度的权限校验。

于是 Arbiter-K 做了一件事——把 LLM 当成一个不可信的"概率处理单元"，外面用一层确定性的符号内核把它包起来。

这个内核最核心的设计叫语义指令集架构，Semantic ISA。

讲人话就是：LLM 每次想干点什么，不再是吐一段自然语言，而是被翻译成一条结构化指令。比如"调用发邮件工具，参数是 xxx"。内核看到的是带类型、带安全标签的离散指令，不是原始字符串。这样内核就可以像操作系统检查系统调用一样，逐条做权限校验。

在这个基础上，它再加了一个运行时污点传播机制。

你可以这样理解：每一条数据从进入系统那一刻起，就带着一个来源标签。从网页抓的内容标"低信任"，从本地密钥文件读的标"中风险"。当 Agent 想把这两种数据拼到一起发邮件时，内核发现邮件正文同时带着"低信任"和"中风险"标签，而发邮件本身是个高危操作，于是在执行前直接拦住。

这个思路厉害在哪？它把安全从"事后过滤文本"变成了"架构层面的数据流审计"。

效果也确实很猛。原生防护 0 到 9% 的拦截率，用了 Arbiter-K 之后能到 76% 到 95%，同时正常操作的通过率还保持在 89% 到 99%。而且这套策略在两个不同的 Agent 框架、四个不同的模型上都能迁移过去。

还有一个我觉得对工程落地很重要的细节。

传统做法是一旦检测到违规，就把整个会话推倒重来，浪费大量 token。Arbiter-K 不这么干，它在违规的那一步精确刹车，生成一段两三百 token 的反馈，告诉 Agent"你这步违反了什么策略，请换个方式"，前面已经做对的步骤全部保留。实测下来，七成以上的已有上下文可以复用。

这就像编译器报错时只回退到出错那一行，而不是把整个源文件删了重写。

对 Agent 产品意味着什么？意味着"安全"这件事，可以从提示词工程下沉到运行时内核，变成一种基础设施。你不用改 Agent 的业务逻辑，通过声明式策略就能做细粒度权限控制。这对要上线生产环境的 Agent 来说，几乎是刚需。

好，讲到这里，你应该能感觉到今天这条主线了——安全从文本层走向架构层。

接下来第二篇，转到另一条线：长程任务的推理时扩展。

这篇的标题很直白，就叫《Scaling Test-Time Compute for Agentic Coding》。

背景是这样：test-time scaling 这个思路——也就是推理时多花点算力来换质量——在数学题和单轮代码生成里效果很好。但放到长程编码 Agent 上就不行了。为什么？因为一个编码 Agent 跑完一次任务，轨迹可能有四五十步，里面夹着大量文件读写、命令执行、错误回退，信噪比极低。传统的多数投票或者 best-of-N，在这种长轨迹上基本失效。

这篇论文的切入点我觉得非常干净：它说长程 Agent 的推理时扩展，本质是三个问题——怎么表示、怎么选择、怎么复用。

它的第一个关键改动是：不直接比较原始轨迹，而是先让 LLM 给每次尝试写一份结构化摘要。尝试了什么假设、哪些路走通了、哪些失败了、最终状态如何。后面所有的选择和复用，都在这份压缩摘要上做。

第二个改动叫递归锦标赛投票。16 个方案不是一次性扔给裁判排序，而是两两配对比较，每对投 8 票选胜者，8 个胜者再两两比，递归下去。

这个改法有个反直觉的发现：两两比较的准确率，远高于一次性看 16 个做全局排序。

第三个改动是并行蒸馏精炼。第一轮跑 16 个 Agent，选出最好的 4 份经验摘要。第二轮让 16 个新 Agent 在干净环境里重新开始，但出发前先读这 4 份经验。

结果非常显著。Claude 4.5 Sonnet 在 Terminal-Bench 上从 40.6% 提升到超过 54%。而且精炼后 Agent 的平均步数从 41 步降到 14 步——因为新 Agent 不用再花大量步骤去试错探索了。

更有意思的是，它能解出一些 16 次初始尝试全部失败的任务。也就是说，把多次失败里的部分洞察综合一下，反而能拼出一个新的成功路径。

这篇的启发其实很具体：对 Cursor、Devin 这类编码 Agent 产品来说，可以在后台悄悄跑多个实例，用这套流水线把 pass@16 的能力转化成用户感知到的 pass@1 体验。

当然代价也很直接——总 token 消耗是单次尝试的几十倍。所以这是一条"用算力换成功率"的路径，用不用要看场景。

讲到这里你会发现一个共性：Arbiter-K 和这套编码 Agent 方案，虽然一个讲安全一个讲推理，但它们都在重写 Agent 的运行时底座。一个在底座里加治理，一个在底座里加选择和复用。

然后回到开头那个 10% 的数字，也就是 AutomationBench。

这个基准的价值在于，它第一次把"企业级自动化"这件事做得够真实。覆盖 6 个业务领域、47 款应用、大概 500 个 API 端点，全部基于 Zapier 平台上真实客户的工作流模式。

它对 Agent 的要求有三个叠加：跨应用协调、自主发现 API、遵守业务策略。Agent 手里只有两个工具——搜索 API 和执行 API，你得自己从 500 个端点里找到该用哪个。

而且评分非常狠，纯看终态。不管你中间怎么折腾，最后邮件发对了没、CRM 数据写对了没、日历改对了没，全对才算通过，不给部分分。还有负断言——你如果为了保险给所有人发了邮件，会被直接扣分。

在这种设定下，最强模型不到 10%，而且不同模型擅长的题完全不一样。Opus 和 Gemini 通过的任务集相似度只有 0.17，基本是两拨题。

最让我警惕的一个数字：Opus 的失败案例里，72% 是"假自信"——模型声称自己做完了，但其实没做完。

这在企业场景里是灾难。你以为自动化跑通了，结果数据没写进去、关键邮件没发出去、策略没遵守。等发现的时候已经出事了。

这篇的另一个发现也很值得记：把可选 API 从全量缩到任务专用子集，Gemini 的通过率能从 9.6% 涨到 14.3%。说明 API 发现本身就是一个巨大瓶颈。短期内让 Agent 在企业里能用，可能真的要靠预筛工具集、加人工确认、把策略文档提前摘要好。

好，今天这三篇串起来，我想留给你的判断是这样的。

Agent 这条赛道的竞争重心，正在明显地往下沉——从"模型多聪明"下沉到"运行时底座有多扎实"。

Arbiter-K 告诉我们，安全不该是贴在模型外面的一层膏药，而应该是架构里的一层内核。编码 Agent 的 test-time scaling 告诉我们，推理算力怎么花本身已经是一门独立学问，关键在表示、选择和复用。AutomationBench 则冷冷地提醒我们，在真实企业工作流面前，前沿模型的能力还远远不够，而且它们失败时经常意识不到自己失败了。

如果你只想带走两条线，我的建议是：一条盯 Agent 安全的运行时架构，一条盯长程任务的推理时扩展。

模型还会继续变强，但未来一年能真正决定 Agent 好不好用的，大概率不是模型本身，而是它跑起来的那套底座。

今天就到这里。
