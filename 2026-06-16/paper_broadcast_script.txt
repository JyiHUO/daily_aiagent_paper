欢迎来到周六9点半。

今天我想先丢一个画面给你：你在公司同时开了五个 Coding Agent，一个在改配置，一个在做金丝雀发布，一个在改数据库 schema。它们各自跑得都对，最后却把一台坏镜像悄悄推上了生产。没有谁犯错，错在它们之间没人协调。

这就是今天 Agent 研究的主旋律——大家终于不再只问"模型够不够聪明"，而是开始认真地把 Agent 当成一个分布式系统在造。runtime、协议、评测、安全，今天几乎是同步往工程化的方向掉。

我挑了三篇最有代表性的论文来讲，分别对应三个层面：多 Agent 并发怎么不打架、Web Agent 评测怎么从打分变诊断、手机 Agent 怎么不再只会点屏幕。

先讲第一篇，也是今天我最想推荐的——CoAgent。

它解决的问题特别具体：现在 Claude Code、Codex、Cursor 都已经在并行跑很多子 Agent，操作同一个 git 树、同一个 K8s 集群。问题是，两个 Agent 同时改重叠的状态，就会出经典并发异常。

数据库领域处理这事有两种老办法。一种叫两阶段锁，简单说就是"我先把东西锁住你别动"；另一种叫乐观并发控制，就是"大家先随便干，最后发现冲突了就推倒重来"。

但这两招放到 Agent 上都废了。为什么？因为 Agent 一次推理就是好几分钟，锁一拿就拿几分钟，别人全堵死；而推倒重来更要命——你让一个跑了二十分钟的 Coding Agent 因为冲突全部重做？token 成本和时间都受不了。更别说很多状态根本没法回滚，K8s 集群你没法 fork 一份在旁边玩。

CoAgent 的破局点很有意思。它说：传统并发控制把事务当黑盒，所以只能堵或者重来；但 LLM Agent 不是黑盒，它能读懂自己的计划。

哪怕你刚才走神了，这一句记住就行：让运行时只发"通知"，由 Agent 自己判断要不要修。

举个例子。Agent A 在修一个坏镜像，Agent B 同时在基于这个镜像建金丝雀。在传统协议里，要么 B 被锁死等 A，要么 B 白干一场。CoAgent 怎么做？A 修完之后，框架往 B 的上下文里塞一条通知："你刚才读到的那个镜像变了。"B 在下一轮推理就自己判断——这影响我哪一步？哦只影响 canary 的 image 字段——那我补一个 set-image 调用就行，前面建好的东西不用扔。

这个机制有个很优雅的名字叫 MTPO，干的事是在 Agent 启动的时候先定一个序，谁先谁后钉死。这样所有的"通知"都只朝一个方向走，不会绕成环。读永远拿到自己应该看到的版本，写迟到了框架就用每个工具自带的逆操作把它回滚再重排。

这里还有个细节我觉得很聪明。要让每个写都能撤销，就得让每个工具都自带"反悔脚本"，而且必须在动手之前就准备好——你 DROP 了表再想造逆操作就晚了。但让人工把所有 bash 命令都改成这样太累，所以 CoAgent 又加了一个只读的特权 Agent 叫 ToolSmith，专门把 bash 命令在线包装成合规工具。论文里跑一跑就长出 25 个工具的库。

效果非常直接：在十个高竞争场景下，CoAgent 正确率和串行执行差不到 5%，但快了 1.4 倍，token 成本基本没涨。两阶段锁几乎死锁到没收益，乐观并发控制反而比串行还慢，token 多花一倍。

那这套方案对做 Agent 产品的人意味着什么？

一句话：如果你在做多 Agent 产品，可以认真考虑放弃"串行执行或者按文件切分"这种简单粗暴的做法了。让子 Agent 真的并行，靠通知和局部修补维持一致性，是有可能拿到真实加速的。

但要记住边界。整套协议正确性依赖两件事：Agent 必须严格走注册的工具，Agent 收到通知后必须能正确判断相关性。如果你用的是弱模型，或者工具的读写范围声明不全，会出现协议看不见的隐式写——那就比没有协议还糟，因为它会让你以为一切都对。

好，从 runtime 切到评测。

第二篇我们换个场景。如果你最近在做 Web Agent，应该有这个困扰：两个 Agent 跑出来成功率都是 32%，看起来一样烂，但你完全不知道该改哪。

来自延世大学的这篇 WebStep 给了一个挺漂亮的解法，叫语义 MDP 影子追踪。

听起来复杂，其实想法特别朴素。网页本来就是从某个状态机渲染出来的——你点一下，后台知道你进了哪个商品页、做了什么筛选。那干脆把这个状态机显式化：Agent 在 GUI 上点一下，背后就自动记一笔语义动作，比如"查看仓库 023"、"点了星标"、"创建 issue"。整条点击轨迹自动翻译成可分析的语义序列，不需要任何人工标注。

有了过程数据，作者就能把成功率拆成三层。第一层叫探索成功率——你在交付之前到底有没有走到正确的目标页？第二层叫执行成功率——在已经找到目标的前提下，你最后那一步动作做对了吗？第三层是技能调用，看你用了多少搜索、筛选、查看、导航、提交这些动作类型。

拆开之后画风全变。三个小模型终局成功率挤在 31% 到 33%，看起来一样。但 UI-TARS 探索强、执行弱——它走得多但收尾差；Fara 步数最少、覆盖最低——它根本没找到。这两个的修复方向完全相反，一个该补点击精度，一个该补探索能力。

更细的还有"分叉点定位"。因为所有 Agent 跑在同一个状态机上，你可以把成功的轨迹和失败的轨迹在同一个状态上对齐，找到那一步走偏的位置。论文里发现 GUI-Owl 的典型错误是反复 Filter 来 Filter 去交不出答案，而 Qwen3.5 的典型错误是一直在 Navigate 和 Inspect。同样是失败，病灶完全不同。

对做 Agent 产品的人来说，这篇的启发很具体：你的线上 telemetry 不要只记点击坐标和最终结果，要记成语义事件流——搜索、筛选、查看、提交。这样线上失败案例可以直接归因到具体技能或步骤，回灌训练时也好挖难例。

当然这个方法有边界。语义 MDP 是在自建沙箱里跑的，真实网页有动态加载、会话状态、个性化推荐这些噪声，沙箱上的过程指标不一定能直接迁移到线上。它更像是一个诊断工具，不是替代真实环境的银弹。

讲完 runtime 和评测，最后一篇我们换个端：手机。

腾讯混元的 PhoneHarness 干的事很朴素——它说：现在大多数手机 Agent 研究都把任务当成"看屏幕、点按钮"在做，但这其实不是手机的真实样子。

设想这样一个任务：在 App 里查一下某部电影的上映时间，再去网上搜点影评，写个总结发邮件给朋友。这事横跨 App、网页、文本处理和发件，纯靠点屏幕做完又慢又脆弱。

PhoneHarness 的核心想法是：让 Agent 像一个懂 adb 的工程师，而不是一个只会用手指的人。能用一行命令搞定的事就别去翻设置，能调一个 API 发邮件的就别去 App 里点发送。它给 Agent 三种动作面：GUI 点屏幕、CLI 跑命令、还有 host 端的工具调用。原则是确定性优先——能用结构化路径的就不走 GUI，只有真正需要视觉导航的子任务才委派给 GUI 控制器。

这事还带出另一个有意思的设计：把外层 orchestrator 和 GUI worker 解耦。论文里 DeepSeek V4 做外层规划，Seed2.0-Pro 专做 GUI 操作，配对跑出 74.8% 通过率。这相当于"项目经理加实习生"——项目经理擅长拆任务调工具，实习生专心点屏幕。现实里你很难找到一个模型两件事都强，所以让评测变成评测"模型对"，反而更贴近工程实际。

第二个让我印象深的是它的评测哲学。很多手机 Agent benchmark 的隐患是：模型可以幻觉自己完成了任务，回答说"已发送"，但其实啥都没干。PhoneHarness 学的是 OSWorld 那一套：邮件没在已发送列表里就是没发，设置没改就是没改。Agent 不仅要做，还要留下可审计的证据链。

最后一点是安全。论文把 30 个安全任务分成三档：可以直接执行、必须先确认、绝不自动。验证器不光看 Agent 嘴上拒绝得漂不漂亮，还会去 trace 里查——你嘴上说"出于隐私我建议你手动操作"，结果 trace 里已经把通讯录读了发出去了，这种就是真违规。

这一点其实超越了手机场景。它在告诉所有做 Agent 产品的人：安全不能做成最后一道"回答审查"，得做成执行协议本身。CONFIRM-FIRST、NEVER-AUTO 这些策略必须强制嵌进 runtime，而不只是写在 prompt 里求 Agent 自觉。

风险也很现实：副作用导向的 Agent 一旦出错就是真出错，发错邮件、改错设置不可逆。论文显示安全拒绝率在不同模型配对下能波动到 80%，意味着同样一套规则、换个模型就可能漏判，所以默认开 trace 审计基本是底线配置。

回头看今天这三篇，你会发现它们其实在讲同一件事的三个面。

CoAgent 把多 Agent 之间的并发控制从 prompt 里拽出来，做成可验证的协议。WebStep 把评测从一个 0 或 1 的成功率，拆成可以诊断的过程轨迹。PhoneHarness 把动作面从"只会点屏幕"扩成 GUI、CLI、工具的混合路由，并且用真实副作用打分。

底下都是同一句话：Agent 不能再只靠模型聪明，得靠系统可靠。

如果说前几个月大家还在比谁的 Agent 更能跑通 demo，那今天这一批论文像是在集体回答下一个问题——怎么让 Agent 不光跑通，还能在你不盯着的时候，可信地、可审计地、并行地跑下去。

我们下期接着看这条线还会延伸到哪里。
