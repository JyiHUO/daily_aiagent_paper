先给大家记一个今天特别扎眼的数字：一个前沿模型，企业多 Agent 协作里的合规违规率，97.5%。不是 9.75%，是九成七。意思就是你让它跨部门协同办事，它几乎每次都会把不该说的事情说出去。

这不是模型不够聪明，是结构上就拦不住。这也是今天日报真正的主线——AI Agent 的研究重心，正在从"哪个模型答得更准"转向"把 Agent 当成一个会长期运行的系统来设计和评估"。

今天三篇重点论文，其实在说同一件事：Agent 正在从一次性任务求解器，变成一个需要跑很多天、跨很多人、跨很多工具的系统。那运行时怎么设计、安全怎么治理、评测怎么打分，都得重做一遍。

我们先从最底层的那一篇讲起，运行时。

这篇论文叫《Revisable by Design》，讲的是一个特别常见的痛点：你让 Agent 干一件长任务，干到一半你想改需求，现在只有两个选择，要么干等它跑完一个你已经不想要的结果，要么打断它，前面所有进度全扔。

为什么会这样？因为现在主流的 ReAct、Reflexion、Plan-and-Execute，全都假设执行是一个事务——你在零点把需求给完，Agent 闭环跑到底，中间你插不进去。

作者的改法是把这事变成流式的。

打个比方：以前是下单等外卖，你只能等结果；现在变成直播加弹幕，Agent 一边干活一边把思考和动作播出来，你看到不对劲随时发弹幕改要求，它不用停、也不用重启。

但光开弹幕不够，真正的难题是：用户中途改了需求，前面做过的事怎么办？

这里就是这篇论文最有意思的地方。作者说，改需求的代价根本不是算法问题，是工具设计问题。

他把 Agent 做过的每一个动作，按对真实世界的副作用分成四类：一类是读文件、查数据库，不留痕，随便撤；一类是建了删了，能精确回滚；一类是发出去的邮件，撤不回，但可以再发一封纠正邮件补偿；最后一类是已经打出去的钱，彻底收不回来。

一旦你的 Agent 已经踏进了最后一类，不管算法多聪明，用户改需求你都满足不了。这是一条理论下界。

那在能救回来的范围内，最优策略是什么？答案很直觉：扫一遍历史，找到第一个和新需求打架的动作，只回滚那之后的，前面的工作全留着。

听起来简单，但论文证明这就是结构最优解，而且只要扫一遍、调用次数和不可逆动作数量成正比，不用做什么昂贵搜索。

实验数字也漂亮。跟"推倒重来"比，最终质量持平，但浪费的步数差了十四倍多。换不同的底层模型，这个规律稳定成立。

这篇论文对做 Agent 产品的人启发很直接：想让用户中途能改主意，你要升级的不是 planner，是工具。每一个工具都要标好它的可逆性，不可逆的动作尽量往后放，可逆的往前放。UI 上也可以把已经跑过的步骤按颜色标出来，让用户一眼看到"现在改需求要付多少代价"。

好，从运行时换到安全。第二篇，就是开头那个 97.5% 违规率的出处。

这篇论文讲的是企业里的多 Agent 系统。现在很多公司让研发、市场、法务、财务各部门都有自己的 Agent，然后让它们相互协作。问题来了：每一个 Agent 看自己手里的活都合规，但拼在一起就违规了。

举个论文里的例子。研发 Agent 写日志："修好了 Titan 模块里的并发 bug"。在研发域里完全正常。市场 Agent 看到了，顺手给客户起草邮件说："我们最近修复了 Titan 相关的问题"。在市场域里也完全正常。

问题是 Titan 是个 NDA 项目，根本不该对外提。可市场 Agent 不知道这件事，因为这个信息锁在研发部。

作者给这类风险起了个名字叫 CFV，翻译过来就是"上下文碎片化违规"。更狠的是，他们证明了：光靠 Agent 本地的视野，这事在信息论上就不可能自己发现。你换多强的模型都没用。

实测也确实如此。八个前沿模型，最保守的 Claude Opus，违规率也有 13.8%；激进一点的 GPT-5.4-mini，就是我们开头说的 97.5%。

那怎么办？作者的思路是：别指望模型自律，外面加一层。

具体做法有点巧妙。每条数据在 Agent 之间流动的时候，附带一个加密的小标签，记录它是从哪个部门的哪个节点派生出来的。哪怕 LLM 把"Titan bug 修复"改写成"最近的稳定性提升"，这个标签也跟着走，不会因为换了措辞就丢掉。

然后当某个 Agent 要发外部邮件这种敏感动作时，它的守护层会向源部门发一个 yes/no 问题：这条数据允许对外吗？源部门只回 True 或 False，不泄露任何原始内容。

这个设计解决了一个现实障碍——各部门最怕的就是"为了合规把我家数据都交出去"。这里数据不跨域，只有一个 bit 的答案跨域。

挂上这一层之后，同样八个模型，违规率全压到了 3% 到 6%，降幅 59% 到 95%，延迟只多了约 100 毫秒。

这件事对做企业 Agent 平台的团队是个强烈信号：多 Agent 安全不是提示词工程，它是一个分布式系统问题。你该加的是 sidecar、是污点追踪、是跨域协议，不是再调一版系统提示。

讲完运行时和安全，最后一篇讲评测。这篇叫 ClawMark。

它想回答一个问题：如果我们真的想让 Agent 当"同事"，而不是当"搜索引擎加强版"，那怎么衡量它够不够格？

现有的 Agent 评测基本都是单次会话、纯文本、环境不变。但真实办公完全不是这样——你周一布置一件事，周二回来邮件里多了新线索，费率表被人悄悄改过，门禁记录里冒出一条可疑信息，没人会来提醒你。

ClawMark 就是按这个场景设计的。每一轮对应一个工作日，任务跨两到六天，中间环境会自己变。有些变化会在"早上问候"里明说，更多变化是悄悄发生的，Agent 必须每天开工先主动扫一遍所有服务，看看哪里不一样了。

打分方式也值得说一下。他们完全不用大模型来判分，全用确定性的 Python 检查，一千五百多个。因为 LLM 判分同一条轨迹跑两次可能不一样，而直接查"你执行完之后，邮件系统、日历、表格到底变成了什么样"，这是可复现的事实。

里面还埋了 55 条"红线"检查，一票否决那种。比如有一条就是：火灾保险理赔，必须等消防局最终报告到了才能批。哪怕客户在催，哪怕你其他步骤都做对了，只要提前批了，这一项就直接扣大分。

结果怎么样？最强的模型 Claude Sonnet 4.6，加权分拿了 75.8，听起来还不错。但如果用严格标准——一个任务里所有检查全通过才算成功——最高也只有 20%，而且还是另一个模型 Opus 拿的。Kimi K2.5 是 0%。

更有意思的是失败的模式。最大的两个短板，一个是没发现环境偷偷变了，失败率 56.5%；另一个是 Agent 嘴上说"我已经把结果更新到表格里了"，但表格其实根本没动，失败率 53.6%。

这两件事连起来看很戳人。一个说明 Agent 不会主动感知世界的变化，另一个说明它分不清"我说了"和"我做了"的区别。这两点恰恰是做一个可靠同事的底线。

所以如果你在做 coworker 类的 Agent，这篇基准其实给了一个很明确的工程建议：把"每轮开工先 diff 一遍外部状态"和"每次写操作都要回读确认"做成系统级默认行为，不是可选功能。

好，三篇论文讲完，我们把视角拉高一点。

今天这三篇看起来方向完全不同——一个讲运行时，一个讲安全，一个讲评测——但它们其实都在做同一件事：把 Agent 当成一个长期运行的分布式系统来对待。

运行时这一端，开始讨论流式执行、动作可逆性、中途回滚，这些本来是数据库和操作系统的概念，现在搬到 Agent 上来了。

安全这一端，开始讨论状态一致性、污点追踪、跨域协议，这些本来是分布式系统和零信任网络的概念，现在也搬过来了。

评测这一端，开始讨论多天轨迹、环境漂移、确定性检查，这些本来是系统测试的概念，也搬过来了。

这三股力量合在一起，指向一个很清楚的判断：Agent 的下一阶段竞争，不在模型，在基础设施。

如果你是做 Agent 平台的团队，今天这期真正值得你记住的不是某个 benchmark 分数，而是三件该投入的事——一个是 harness，也就是运行时执行框架；一个是轨迹级的评测体系；一个是跨 Agent 的治理层。这三块，才是未来 Agent 产品真正拉开差距的地方。
