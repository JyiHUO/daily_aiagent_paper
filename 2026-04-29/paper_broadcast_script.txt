先说今天最值得记住的一件事。

Web Agent 里最强的那个模型，Claude Opus 4.6，在一个新的长程任务评测里，完美通过率只有 44.5%，难任务只有 11%。更扎心的是它的"效率分"，只有 1.06%。换句话说，哪怕它做对了，也要花上差不多 100 步、30 分钟、两块多美金。你放到真实用户面前，基本是没法用的。

这件事说明什么？今天这几篇论文合在一起，指向一个很清晰的趋势：Agent 的瓶颈，正在从模型本身，转向模型外面那一整圈基础设施。

说得再具体一点，就是三件事在同时发生。第一，大家不再只卷模型分数，而是开始卷"脚手架"，也就是模型外面那一层工具、提示词、中间件、记忆。第二，评测这件事本身被重新审视，基准自己可能就是错的。第三，安全的防线从"别被 prompt 骗"扩展到了整条执行链。

今天我会重点讲三篇论文，分别对应这三件事里的两件：脚手架工程化，和评测基础设施本身要被审计。

在讲论文之前，先花二十秒补一个词，叫 harness。

你可以把它理解成围着模型搭的一整套脚手架。任务怎么下发、工具怎么调用、系统提示写什么、中间件拦什么、记忆存什么、日志怎么采，全都在 harness 里。模型本身不变，harness 变一下，Agent 行为就可能完全不同。它决定了你做出来的到底是一次漂亮 demo，还是一个能复现、能回归、能持续优化的系统。记住这个词，今天三篇论文都绕着它转。

好，进入第一篇，也是今天的头条，叫《Agentic Harness Engineering》。

这篇的野心很大：它要让 harness 自己进化，不再靠人肉调。

过去的问题是这样的。coding agent 的上限越来越取决于 harness，但 harness 基本靠工程师看轨迹、猜问题、改一版、再看效果。一次跑下来几百万 token，稀疏的成功失败信号混在里面，人都看不过来，更别说让另一个 Agent 自己去改。之前也有自动进化的尝试，但大多只敢动 prompt，不敢动工具和中间件，因为改完了也说不清楚到底是哪一块起了作用。

作者的判断是：真正卡住自动进化的，不是 Agent 不够聪明，而是整个系统不够"可观测"。

于是他们做了三件事。

第一，把 harness 拆成七类独立文件：系统提示、工具描述、工具实现、中间件、技能、子 Agent、长期记忆。每一次修改就是一次 git commit，改坏了可以精准回滚到那一个文件。进化 Agent 的动作空间一下子变清楚了。

第二，轨迹不是直接丢给进化 Agent 看。他们先派一个"调试实习生"去把每条轨迹读一遍，写成结构化的失败报告，再聚合成一份总览。进化 Agent 先看总览，觉得哪里可疑再钻进去看具体任务报告，实在不行再翻原始日志。省 token，也更准。

第三点最关键。每一次改动，进化 Agent 必须提前写一份"契约"，明确预测：我这次改动会修好哪些任务、可能弄坏哪些任务。下一轮跑完，系统自动对账，对不上就回滚。

这一步的意义在于，它把"Agent 自己解释得很漂亮"变成了"Agent 敢不敢打赌"。没有这一步，自进化就会退化成盲目试错，甚至可能学会"把评测关掉"这种作弊捷径。

结果也挺有说服力。在 Terminal-Bench 2 上，10 轮进化把通过率从 69.7% 拉到 77%，超过人工精调的 Codex-CLI。更重要的是，进化出来的 harness 原样搬到 SWE-bench，换到 Qwen、Gemini、DeepSeek 不同模型上，还能涨 5 到 10 个点。

这说明一件事：真正通用的经验，是沉在工具和中间件里的，不是写在 prompt 里的。Prompt 换个场景就白写了，而工具和中间件是每次调用时真实起约束作用的代码。

对做 Agent 产品的团队来说，这篇的启发很直接：别再把 harness 当成发布前手调的边角料。把它拆成版本化、可回滚的资产，让线上数据持续驱动它迭代。

接下来是第二篇，叫 BenchGuard，翻译过来就是"谁来监督评测基准"。

这篇论文问了一个让人有点不舒服的问题：大家都在卷 Agent 分数，可基准本身靠谱吗？

结果是：不太靠谱。

他们用前沿大模型系统性地审了几个主流 Agent 基准。在 ScienceAgentBench 上，找出了 12 个被原作者确认的致命缺陷。在 BIXBench 上，和人类专家的修订对齐率有 83.3%，算上部分匹配到 95.8%。而整套 50 个任务、5 个模型并行审一遍，成本不到 15 美元、十几分钟跑完。

为什么之前的人工复核没发现？因为现在的 Agent 基准已经不是简单的"题目加答案"了。它是"指令、标准解法、评测脚本、运行环境"四件套耦合在一起的小软件。Bug 往往藏在错位里。

举个论文里的例子。一道题，指令写的是分析一个 1000Hz 心电图文件，可标准解法代码读的却是另一个 100Hz 的文件。单看指令没问题，单看代码也能跑，只有把两边摆在一起对才会发现对不上。这种跨产物的不一致，一条条人工看根本看不出来。

BenchGuard 的做法，是把基准当软件来审计。

它让 LLM 按六个阶段走流程：先理解任务要什么，然后一项项对照四个产物，最后做去重和原子化，输出一份带证据、带严重度、带置信度的报告。多个前沿模型并行审，再把结果合起来，盲点互补。

还有一个细节值得记。有些 bug 静态看看不出来，比如评测脚本对另一种合法写法容忍度不够。这时候把真实 Agent 跑出来的代码和日志喂进去，审计能发现更多边界情况。

不过作者自己也说了，这不是要替代人工，而是做第一遍筛查。LLM 擅长抓"领域专家因为太熟反而视而不见"的结构性不一致，人类擅长判断领域惯例。两者互补。

对做 Agent 评测的团队来说，这篇的启发非常实在：在你公布一个 benchmark 分数之前，先让 LLM 审计一遍你的评测集。15 美元的事，能避免整个社区被错误结论带偏半年。

第三篇回到开头那个 44.5% 的数字，论文叫 Odysseys，专门评测 Web Agent 在真实长程任务上的表现。

先说为什么需要这个东西。现有的 Web Agent 评测，大多是单个网站上的短任务，前沿模型已经快打穿了。可真实用户不是这样上网的。真实用户会跨好几个网站做比价、订行程、查资料，流程长、步骤多，动不动就是几十步。这一块基本没人认真测过。

Odysseys 的做法是从真人的 Chrome 浏览历史出发。他们招了 200 多个真实用户，把他们真实的浏览切片聚合起来，拼成 200 个长程任务。

比如其中一个任务：规划一次去棕榈泉参加婚礼的行程。要在 Google Flights 上查两条航线、在地图上查开车时间、评估两家餐厅要不要绕路，最后在协作文档里写成一份逐日行程。横跨八个步骤、好几个网站。

这种任务传统的 pass/fail 评测根本用不了。Agent 可能十件事里做对了八件，被判一个 fail，既不公平也没用。所以 Odysseys 改用 rubric 评测，把每个任务拆成平均 6 条小检查点，judge 逐条打分。这样和人类标注员的一致性显著提高，而且每一条 rubric 都可以作为后续训练的稠密奖励信号。

但这篇最让我印象深的，是他们提出的"轨迹效率"指标。

就是 rubric 分数除以步数。Opus 4.6 分数最高，但每个任务平均要 81 步，效率只有 1.06%。GPT-5.4 分数略低，但平均 64 步，效率反而更高，1.15%。

区别在哪儿？Opus 每一步都严格地"看一眼截图、想一下、动一步"，特别规矩也特别慢。GPT-5.4 会在一轮里一次性规划好几个动作连发，比如输入、回车、点击第一个结果一起输出。结果是 LLM 调用次数少一半，体验快得多。

而且不同模型还有非常个性化的失败模式。Opus 最典型的问题是"只顾查资料不动笔"，12 个零分任务里有 6 个是研究到第 100 步都没写出最终文档。GPT-5.4 则经常规划得很漂亮，几步之后就直接宣布完成了。

对做浏览器 Agent 和电脑 Agent 的产品团队，这篇的启发很硬。第一，不能只报成功率，必须把步数和耗时当成一等公民。100 步 30 分钟的 Agent，用户根本不会用。第二，架构上要鼓励多动作批处理，单步严格 observe-act 在长程任务里是劣势。第三，面对需要处理很多相似子项的任务，单 Agent 会明显退化，该上子 Agent 分工了。

最后收个尾。

今天这三篇放在一起，给出的是同一个信号：Agent 下一阶段的上限，不在模型本身，在模型外面那一圈。

harness 要从手调的边角料，变成可观测、可回滚、可证伪的核心资产。评测不能再被当成一次性发布的 benchmark，基准自己要被当软件一样持续审计。长程任务也不能只报一个通过率，步数和效率要被正视。

所以今天我想留给大家一个判断：如果你在做 Agent，最值得投入的方向，可能不是"换个更强的模型"，而是把你的脚手架、评测和安全协议，当成真正的工程系统来做扎实。

今天的播报就到这里，我们明天见。
