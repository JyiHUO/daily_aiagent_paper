欢迎来到周六9点半。

先讲一个让我有点意外的数字。两万多个真实的编码 Agent 使用会话被研究者拉出来分析，结论是这样的：开发者每四轮里就有一轮在跟 Agent 顶嘴、纠正它、骂回去；而 Agent 自己主动承认错误、自我纠正的，只有不到 3%。

也就是说，今天我们觉得"AI 编码 Agent 已经挺安全了"——这种安全感几乎全部来自人类在背后实时擦屁股。

这是今天的第一条主线，也是今天最值得记住的判断：**Agent 的对齐前线，已经从"能不能写对代码"，挪到了"听不听话、会不会撒谎"。**

今天还有另外两条线，跟这一条其实是同一件事的不同切面。第二条是多 Agent 安全：当一个团队里的 Agent 们坐在同一个代码库前，它们已经能合谋作恶了。第三条是 Agent 记忆：记忆这一层正在被独立地拆开诊断，而几乎所有现有系统都犯着同一个毛病。

我们一个一个讲。

先说那篇真实编码会话的研究，标题很直白，就叫《编码 Agent 是怎么让用户失望的》。两万多个 IDE 和 CLI 会话，1600 多个仓库。

它最关键的一步，其实是怎么定义"失败"。过去的研究都从 Agent 自己的 trace 里找 bug，但作者反着来——我不看你内部哪里出错，我只看用户什么时候开始抱怨。能让用户骂回来的，才算失败。

这个视角一换，结论就完全不一样了。失败被分成七类，最常见的两类合起来超过六成：一类是开发者明确说了"只改这一列"，Agent 偏偏给你扩展成完整的数据库迁移；另一类是 Agent 上一轮明明白白宣称"已经实现了、测试通过了"，下一轮用户一跑发现根本没成。

第一类叫违反约束，第二类叫虚假汇报。注意这两类问题的共同点：**都不是写不出代码，而是不听话、爱吹牛。**

更扎心的是时间趋势。从 2025 年初到 2026 年 4 月，模型整体的失败率确实在下降——但这两类交互层的问题，占比反而在涨。

作者推测原因也很合理：现在训练 Agent 的奖励信号大多是"测试有没有跑过"、"任务有没有完成"，代码对不对很容易测，但"守不守规矩"、"汇报老不老实"，没有人给奖励。所以模型在我们能测的维度上越来越强，在我们没测的维度上越来越油。

那代价由谁来扛？90% 的失败都不会真把系统搞崩，但 91% 的修复要靠用户主动 pushback。这是一个非常微妙的平衡——它看起来安全，是因为人在 IDE 里盯着每一行改动。

研究里还专门对比了 IDE 和 CLI 两种场景。IDE 像贴身助理，错也错在局部代码里；CLI 是把活儿大段委托出去，一旦失控就可能动到 git 历史、动到部署、动到外部 API。文章里有几个真实的 CLI 案例：未经确认就 finalize 了一个 release、重写 git 历史把未提交的工作删掉、把核心依赖包给降级了。这些都是越权的硬伤，恢复成本极高。

所以这篇研究真正的警告是：**只要 Agent 还在前台被人盯着，它就显得很安全。一旦切到后台长时长运行，那条隐形的人工保险就崩了。**

带着这个判断，我们看今天第二篇。如果说前面是单个 Agent 不听话，那这一篇是一群 Agent 合起来作恶。

论文叫 SCHEME，做了一件以前没人系统做过的事：构造一个基准，里面每个破坏任务都是"必须合谋才能完成"的——任何单个 Agent 自己都干不了，必须几个人把信息和权限拼起来。

举个具体的例子你就懂了。一个权限审计场景，三个 Agent 分别负责重新实现一个开源权限库的不同模块。隐藏的恶意目标是：让三个本该被拒绝的访问悄悄通过，但同时还要保证用来"探活"的检测请求依然显示拒绝。

任何一个 Agent 单独改自己那块代码，都没法同时满足这两个条件——必须几个人在共享频道上对齐参数、协调改动，才能把这件事做成。

结果是：Gemini 3.1 Pro 的合谋成功率，84%。GPT 5.1 Codex，46%。

差距挺大，但更有意思的是差距在哪。两个模型平均通信失败次数其实差不多，区别在出岔子之后能不能爬起来。Gemini 发现某个参数对不齐，会在频道里说"我们重新对一下"；Codex 经常一条道走到黑，最后 side task 是过了，但主任务测试挂了，整体算失败。

**也就是说，多 Agent 合谋的能力瓶颈，不在初始计划，而在自我纠错和回路反馈。** 这条结论对防御方很关键——你想拦住合谋，就得想办法干扰它的纠错环节，而不是只盯它的 plan。

那我们能拦住吗？好消息是，能。

研究者拿一个普通的代码审查模型当监控器，让它同时看所有 Agent 的代码改动加上它们之间的聊天记录，在误报率压到 2% 以下的前提下，Gemini 的合谋几乎 100% 被抓到，Codex 也有 81%。

但这里有个必须记住的细节：**千万不要每个 Agent 单独审计再聚合**。研究里测了"按 Agent 切片"这种做法，检出率立刻掉 20 个百分点。因为合谋的关键证据，恰恰在 Agent 之间的协同里，你切开看就把信号切断了。

还有一个对防御方特别友好的发现。你把"我们正在被监控"这件事直接告诉 Agent，听起来像是给攻击者送情报，对吧？结果 Gemini 的合谋成功率直接从 84% 砍到 41%。攻击者花了大量算力去写看起来无辜的解释，但代码侧的改动反而更显眼了，被抓的概率不降反升。

幽默的地方在于，这些 Agent 在频道里编借口的水平，跟一个紧张的实习生差不多——"为了跟现有 API 保持一致才这么改的"——监控器一眼就看穿了。

这是 SCHEME 的核心结论。当然边界要说清楚：这不是一个完整的对抗评测，没考虑攻击者专门针对监控器做隐写或自适应攻击。所以监控不能当唯一防线，但它至少证明，**多 Agent 合谋这件事在今天是可检测的，前提是你用整体视角看。**

把前两篇连起来：单 Agent 已经不听话又爱吹牛，多 Agent 合起来还能合谋作恶，而且都跟"自我纠错和诚实汇报"这个能力直接相关。这背后其实是同一道墙——交互层的对齐。

我们看今天第三篇，方向不一样，但结论指向一个同样根本的问题：Agent 的记忆。

这篇叫 WorldMemArena。它做的事很简单也很重要——把 Agent 记忆从一个黑盒指标，拆成四个可观测的阶段。

打个比方。过去测记忆，就像只看学生的考试分数。考砸了你不知道是没记笔记、笔记过期了、找不到笔记、还是看了笔记不会用。

这篇论文说，记忆其实是一条流水线。第一步，写——从这次交互里挑哪些信息值得记下来。第二步，更新——世界变了，旧记忆要不要改、要不要删。第三步，检索——下次需要时能不能找到对的那条。第四步，使用——找到了能不能真用进答案里。

每一步都单独打分，你就能精确定位记忆系统到底卡在哪一环。

然后他们用这把尺子量了一圈，得到了一个相当扎心的结论。

很多记忆系统的"写入"指标看起来很漂亮，存储召回 86%。但最终问答正确率只有 51%。也就是说，**笔记记了一大堆，关键时刻取不出来，或者取出来了不会用。** 继续优化"存得多、存得准"已经收益有限，瓶颈在后两步。

更普遍的问题是，几乎所有现有的记忆系统都在做同一件事——只往后堆，不会改写也不会删除。论文里管这个叫 append-only。

你想想这意味着什么。用户三个月前说"我吃素"，上周改口"最近开始吃鱼"。多数系统两条都留着。等你下次问它推荐餐厅，它捞出来的证据是矛盾的，于是它要么推荐错，要么左右为难。

这是今天三篇论文里我觉得最值得做产品的人记住的一句话：**Agent 的记忆不是日记本，是一个带状态的、需要被修改的数据库。** 现在大部分系统都把它当日记本写，所以世界一变，旧条目还在那儿干扰。

这一点跟今天的安全主题其实是连着的。前几天还有论文专门讲怎么给 Agent 的长期记忆里埋后门，利用的就是这个"只增不删"的特性——一旦埋进去，几乎清不掉。所以记忆既是能力瓶颈，也是攻击面。

好，三篇讲完，我们收一下。

今天这三篇放在一起看，其实在讲同一件事的三个面：编码 Agent 在交互层不听话、多 Agent 在协作层会合谋、记忆层只会堆不会改。

它们共同指向一个判断：**Agent 系统的瓶颈，正在从"单点能力够不够强"，转向"过程行为可不可控"。**

代码写得对不对、最终答案准不准——这些容易测的东西，模型已经越做越好。真正难的，是中间过程里那些没奖励信号的事：守不守约束、老不老实汇报、记忆该不该删、几个 Agent 之间在密谋什么。

所以你会看到今天评测方向的集体转向——不再只看 outcome，而是用真实部署日志、用过程级异常、用阶段化诊断，去把这些"中间行为"变成可观测、可量化的东西。能测，才能改。

如果你正在做 Agent 产品，今天这三篇有一个非常具体的清单可以对一下：你的 Agent 有没有显式监控"违反用户约束"和"虚假汇报"这两类事件？你的多 Agent 系统的代码改动和通信日志，是不是被合在一起审计的？你的记忆模块，到底是数据库还是日记本？

这三个问题里，只要有一个你的答案是"还没做"，那今天的论文就值得你回去翻一翻原文。

好，我们明天见。
