欢迎来到周六9点半。

先给你一个数字。同样三个前沿模型，跑同一个 SWE-bench 测试集，只换外面那层执行框架，分数能动十三个点；只换模型，分数只动两三个点。换句话说，今天 Agent 圈子里大家在拼命比的"哪个模型更强"，可能从一开始就比错了对象。

今天三篇重点论文，从架构、评测、训练三个角度同时指向同一个判断：Agent 的下一个瓶颈不在模型，而在模型外面那一圈系统。这一圈东西，论文里有个统一名字，叫 harness，可以理解成"脚手架"——上下文怎么拼、记忆怎么存、工具怎么调、错误怎么兜、什么时候停。过去这些都被当成工程细节，今天它们被正式抬上一等公民的位置。

我们先从最有冲击力的那篇说起，叫《Stop Comparing LLM Agents Without Disclosing the Harness》，标题就很有态度——别再不公开脚手架就比 Agent 分数了。

作者做了一个特别干净的对照实验。三个能力相近的前沿模型，三套不同的脚手架，从最简单到最完整，各自配对跑一遍。结果是脚手架带来的方差是模型方差的七点八倍。九对横向比较里，有六对的排名会因为换脚手架而翻转。

这个数字什么意思？意思是你今天看到一篇论文说"我们的模型比对手高三个点"，这三个点的真正来源很可能根本不是模型，而是他们悄悄换了一套更聪明的执行框架。而这套框架，论文里通常一个字都不写。

作者还顺手用控制论的语言重新讲了一遍 Agent 是怎么回事。模型本身其实是开环的——它看不到真实状态，只能看到脚手架喂给它的那段上下文；它没有跨步记忆，错了也不会自动改。所以一次长任务能不能稳住、能不能从工具报错里恢复，本质上是外面那圈控制逻辑在决定。模型再聪明，也救不了一个反馈回路设计糟糕的系统。

那怎么办？作者没要求大家统一用一个脚手架，而是提出一个"Harness Card"——你用了什么执行层，必须像写超参那样写清楚，从工具配置到重试策略到验证机制，七个维度全部披露。同时鼓励做模型乘脚手架的网格实验，把方差拆给读者看。

这篇的边界在哪？它的实验只跑了 SWE-bench 一个子集、三个模型、三个脚手架，规模不大。但作为一篇立场论文，它的目的不是给你一个新算法，而是把一个长期被忽视的问题钉在墙上。

对做 Agent 产品的人，这篇的实际含义其实很扎心：与其每个月追新模型，不如先把上下文压缩、工具裁剪、重试和验证回路打磨好，收益往往大得多。Vercel 之前把工具从十五个砍到两个，成功率从八成直接到满分，就是同一个信号。

顺着这条线，我们看第二篇，叫《From Model Scaling to System Scaling》。如果说上一篇在敲警钟，这一篇就是在画蓝图。

作者的主张是：别再把 Agent 想成"模型加 prompt"，要把它当成一个分层系统。他把 Agent 拆成六个组件——基础推理、记忆、上下文构造、技能路由、编排循环、验证治理。每一层都可以单独优化，也可以单独搞砸。

我举个具体例子你就懂了。让 Agent 修一个代码仓库的 bug：编排层启动循环；上下文层从记忆里取出"loader 在某某文件"这条旧记录，再去当前代码里 grep 一下；模型生成补丁；技能路由调"运行测试"这个子 Agent；最后验证层检查权限和测试通过，才把"此 bug 已修复"写回记忆。任何一层缺位，同一个模型表现得都会像一个完全不同的 Agent。

作者重点点了三个最痛的瓶颈。

第一个是上下文治理。更长的窗口不等于更好的上下文。关键是每一步只装最小够用的信息，并且能追溯来源。你给模型塞了三万 token，它真正读进去的可能只是开头和结尾——这是已知现象。

第二个是可信记忆。这个特别关键。记忆不是存得多就好，存进去的东西会过期、会漂移、会被污染。比如 Agent 记着"data loader 在 utils 某某文件"，但代码重构后这个文件已经被删了。语义检索还是会把这条排到最前——如果系统直接信任并调用，就会引入回归 bug。

正确的做法是：每条记忆带上置信度和时间戳，检索时附带过期惩罚，必要时回当前环境二次核对。

第三个是技能路由。子 Agent 多了之后，经常出现"它给了个看起来对的结果，但没人复查"的失败。所以路由必须配后置检查。

讲完架构，作者还顺手把评测也重写了一遍。他说现在的榜单只看任务最后通没通过，忽略了用了多少 token、改了几次、回滚了多少次、记忆有没有越用越脏。但真实部署里这些才决定成本、信任和安全。

想象两个 Agent 都解出了同一个任务，A 用了 5 次工具调用、轨迹干净，B 用了 30 次调用、写入了 10 条互相矛盾的记忆。一次性成功率上两者并列。但跑第二轮类似任务时，B 会因为记忆污染而崩溃。这个差异，单分数榜单看不出来。

这篇论文的局限性也很明显——它本身是一篇综述加观点，没有提供具体的算法贡献，提出的 CheetahClaws 也只是参考实现，不是 SOTA。但它的价值在于把一堆零散的工程实践抽象成了一个可以共同讨论的语言。

这两篇放一起看，其实是同一个故事的两面。一篇说"你们现在的比较方法是错的"，一篇说"那么正确的设计对象应该是什么"。

换个方向，我们看今天第三篇，《CUA-Gym》。这篇是给电脑使用 Agent，也就是 Computer-Use Agent，做训练基础设施的。

背景先说一句。数学和代码领域之所以最近进步快，是因为有大规模可验证奖励的训练数据——题目对就是对，错就是错，机器自动判。但 Computer-Use 不一样。一条训练样本是任务指令、可执行环境、奖励函数三件套，每条都得工程师手写，规模上不去。

CUA-Gym 想解决的就是这个。它的做法挺巧妙。

第一招，是把"造环境"和"写奖励"交给两个不同的 Agent，中间加一道信息墙。如果同一个 Agent 既造环境又写打分，它很容易写出"检查我刚才那几步有没有跑过"这种假奖励——形式上对了，实际上根本没在判断任务有没有完成。论文把两个角色拆开：造环境的人不告诉打分的人具体怎么造的，打分的人只能根据任务描述本身去判断。

举个例子。任务是"按 Notion 名单给每个客户发带附件的邮件"。一个 Agent 去准备 Notion 数据库、Gmail 模板和桌面文件；另一个 Agent 只看任务描述，独立地把奖励拆成"Sent 文件夹有邮件"、"内容匹配模板"、"收件人匹配 Notion 名单"三个子项。两边迭代到能区分初始态和黄金态，这条数据才算合格。

第二招，是干脆让 Agent 自己照着真实应用造一批高仿单页应用。真网站没法当训练场——登录限流、状态不能重置。所以作者让 Plan、Dev、Web 三个 Agent 配合，自动造出 94 个模拟应用，每个都像游戏存档一样能注入初始状态、按 session 隔离。同一个 Mail 应用可以一秒切换成"空收件箱"、"截止日紧张"、"积压一堆邮件"三种世界。

最后训练出来的模型，在 OSWorld 这个标准测试上，从 54.5 涨到 62.1，更大的版本从 62.2 涨到 72.6，而且在完全没训过的 WebArena 浏览器环境上也有提升，说明在模拟器里学到的东西能迁到真站点。

还有一个挺有意思的副产品。RL 训练自发让模型学会了"多动作合并"——没人显式教它，但因为超时会扣分，模型自己发现像点 File、点 Export、点 PDF 这种结果可预测的连招可以一次性发出去；而依赖网络返回或弹窗的动作仍然单步执行。等于训练让推理时延降了三到四成。

当然这套也有边界。奖励只校验终态，区分不了"干净完成"和"先破坏再重建到同样终态"；模拟应用没有真实的鉴权、限流和服务异常，跨到真实生产环境还是会掉点。

好，三篇讲完了，我们退一步看今天的整体信号。

如果你最近一直在追 Agent 这条线，会发现过去两周大家其实都在零散地讨论同一件事：runtime 不够好、记忆会漂移、评测看不出差异。今天这三篇是一次集体定调——Stop Comparing 用方差证据告诉你"模型层面已经被高估"，Harness Scaling 给你一份系统层的设计蓝图，CUA-Gym 则在 Computer-Use 这条具体赛道上把"可验证训练环境"造好了。

合在一起的判断是这样的：Agent 这一年的红利窗口，可能不在等下一个更大的模型，而在把模型外面那一圈系统打磨成型。上下文治理、可信记忆、技能路由的后置验证、harness 的可披露和可复现——这些过去被当成工程细节的东西，正在变成新的研究对象。

所以今天给你带走的具体动作建议是：下次看到一篇 Agent 论文报了 SOTA，先别急着信。去问三件事——他们的执行框架是什么、记忆策略怎么设计的、验证层有没有。这三件事不公开，分数比较就没有意义。
