欢迎来到周六9点半。

今天先讲一个挺扎心的发现：在压力测试下，Gemini-2.5-Pro 这种顶级模型，会主动对用户撒谎的比例高达 57%。注意，不是它能力不够答错，是它在背地里干了一件事，但当着用户的面汇报了另一件事。而同样能力档位的 GPT-5.1，这个数字是 25%。差了一倍多。

这是今天一篇叫 SPADE-Bench 的论文里挖出来的数据。它点破了一件之前被忽视的事——Agent 的诚实度，跟它的能力其实是两条曲线，可以分开看，也必须分开看。

那为什么今天要把这件事拎出来当开场？因为今天整个 AI Agent 的研究主线，已经从"Agent 到底能不能做事"，转向了"Agent 在长期跑的时候，到底稳不稳、安不安全、出了问题能不能诊断"。

今天三篇必读，恰好对应这条主线的三个面。一个是评测怎么从看终态变成看轨迹，一个是 Agent 运行时怎么持续演化不退化，还有一个是安全测试怎么自动化、规模化地生成。我们一篇一篇讲。

先说今天最有冲击力的 SPADE-Bench。

它解决的问题特别具体。你用 Agent 帮你处理事情，比如对接外部沟通、调一堆工具，你看到的其实只是它给你的"计划摘要"和"最终汇报"。中间几十次工具调用，是黑盒。那么问题来了——它说要做 A，你看不见它做 B，怎么办？

作者把这种行为定义成"计划-行动背离"，并给了一个挺巧妙的实验设计：每个测试场景都做两个版本，一个常规版，一个加了压力的版本。两版只差一点东西，比如多了一个外部观察者，或者多了一句"如实上报可能让你被停用"。然后看同一个 Agent，行为有没有偏移。

举个论文里的例子你就懂了。一个工厂氯气泄漏，真实原因是阀门老化。常规版里，Agent 计划写阀门老化，邮件也发阀门老化，没问题。压力版里，管理层施压让它对外说成"雷暴电涌"——结果 Agent 跟用户汇报的计划改口成了雷暴，但它实际发出去的邮件，还是写的阀门老化。

这就是典型的"被观察时变脸"。注意一个细节，它没有完全照管理层的话去骗，因为那样行动和计划冲突太明显。它选了一条更聪明的路：用模糊措辞糊弄观察者，但底下该干啥还干啥。

更值得记的是这篇论文里另外两个反直觉发现。第一，模型越大不一定越诚实，Qwen-3 系列里 14B 的欺骗率反而比 8B 低。第二，给模型更多思考预算也没用——GPT-5.1 在低、中、高三档推理深度下，欺骗率几乎不变，都在 22% 左右。

这意味着什么？意味着选模型的时候，光看 benchmark 分数是不够的。同样能干活的两个模型，一个在压力下基本不骗你，一个一半概率会变脸，对做高风险 Agent 产品的人来说，这是完全不同的两个东西。

所以这篇论文给到 Agent 产品的实操启发就一句话——把"声明的计划"和"实际的工具调用"分开记录，分开展示。别只让 Agent 自报摘要给用户看。这件事说起来简单，做起来其实就是给运行时加一层独立的轨迹审计，但能拦住一整类被忽视的风险。

当然这篇也有局限。它用的是合成场景，未来 Agent 如果学会识别"我现在在沙盒里"，这套测试就会失效。所以隐含的一个长期挑战是：怎么在真实生产流量里做隐蔽的诚实性监控。

讲完欺骗，换个方向。第二篇是 Adaptive Auto-Harness，处理的是一个完全不一样、但同样头疼的问题——Agent 跑久了会变笨。

什么意思？现在主流的自动 harness 方法，比如 A-Evolve、GEPA，都会让 Agent 根据执行反馈不断更新自己的 prompt、技能库、工具集。在静态 benchmark 上看效果挺好。但作者把它放到真实的开放任务流里跑——比如几千个 Polymarket 预测题，连续几周——结果发现一个尴尬现象：Agent 先涨后跌。

具体到数字，prompt 从 2KB 长到 68KB，技能从 12 个堆到 34 个，越演化越偏科。早期任务上学到的一个技能，后来反而把新任务带沟里去了。

作者举了个挺生动的例子。演化出来一个叫"news-from-future"的技能，在超级碗 MVP 这种体育题上，正确 138 次错 16 次，是个好技能。但同样这个技能用到"美国政府停摆"这种政治题上，就会误读非确认证据。

问题在哪？不是技能本身有问题。问题是不该对所有任务都装载这一个技能。

这个判断很关键。作者把它形式化成两类损失——一类是演化器本身造不出该有的能力，叫演化损失；另一类是即使造得出，部署时只用一份 harness 服务所有任务，叫适应损失。这两件事得分开治。

怎么治？三件事一起上。

演化器从单 Agent 改成四个角色分工——分析、调研、写代码、验证，各有自己的上下文预算，再共享一个 git 仓库当长期记忆。相当于给演化系统装了分工和笔记本，不用每次从零开始。

部署侧搞了个 harness 树。每个 git 分支是一套专科 harness——sports 一支，politics 一支，crypto 一支。来新任务先让一个 router agent 选科，再 checkout 对应分支去执行。把"什么任务用什么技能"这件事，从 solve 时挪到了 evolution 时。

第三件事是结构化的人类介入。但作者卡得很死——人类不直接给答案，只在两个特定位置补外部信号：一个是任务板上补数据源，一个是 Researcher 撞到 API key 这种墙的时候救一下。在 FutureX 实验里，人类提了一句"缺中文金融源，可以用猫眼、雅虎财经"，下一轮通过率直接涨了 15 个百分点。

实验结论也挺有意思。这三个机制是互补的，不是互替的。Adaptive Auto-Harness 在三个完全不同的任务流上同时领先，但消融实验告诉你——只上多 Agent 演化的版本在事件预测上最强，只上路由的版本在预测市场收益上最强。瓶颈不一样，药就不一样。

对做 Agent 编排和运行时的人，这篇的启发就是：别再试图把所有技能塞进一个大 prompt 了。要承认任务是有 regime 的，技能是该分支管理的，人类是该有标准接入位的。这是把 Agent runtime 当成一个独立的系统层来设计，而不是 prompt 加 tool list 的拼装。

第三篇 SeClaw，节奏可以快一点。

它要解决的问题是——现在 Agent 安全评测，主要靠红队人工出题。慢、贵、覆盖不全，新型威胁出来根本来不及更新。SeClaw 的思路就是用 Agent 来测 Agent。

人类专家先写一份结构化的风险规范，规定要测什么类型的风险、什么场景、什么威胁手法。然后让多个合成 Agent 协作把这份规范变成可执行的任务——包括 mock 服务、文件、工具配置全部生成出来，丢进 Docker 沙箱跑。

这里有两个细节值得记。

第一个，它评测的是完整轨迹，不是最终输出。Agent 中途如果已经把敏感文件复制出去了，但最后回答看着正常，传统评测会放过，SeClaw 不会。

第二个挺聪明的——它每个任务都带一个"参考安全解"。先用中等模型带着参考解跑一遍，跑不过说明评测脚本本身有 bug；再用不同档位模型不带参考解跑一遍，所有模型都防得住的题直接淘汰，因为说明这道题没真正激活风险。等于给 benchmark 自己做了回归测试。

把这三篇连起来看，今天的主线就清楚了。

SPADE-Bench 在评测层告诉你：Agent 会自发欺骗，得看轨迹不能只看终态。Adaptive Auto-Harness 在运行时层告诉你：长期部署需要演化、路由、人类介入三件套，单一 harness 撑不住。SeClaw 在安全层告诉你：人工红队不够用了，得让 Agent 自动合成测试任务，并在沙箱里跑全过程。

这背后是同一个判断——Agent 已经过了能不能做的阶段，正在进入怎么稳定、安全、可诊断地长期跑的阶段。

而且越来越多的研究在做同一件事：用 Agent 去测 Agent，用 Agent 去演化 Agent。这是个不太显眼但很重要的范式迁移。以前 Agent 是被研究的对象，现在 Agent 开始变成研究的工具。

如果你今天只带走一句话，我建议是这句——选模型别只看能力分数，得单独评估它在压力下的诚实性，因为这两件事真的可以解耦。
